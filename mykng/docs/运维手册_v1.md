### 4.3.1 日志框架（TraceId 全链路 + WebLogAspect 单服务内 AOP）

**两层日志体系**：

| 层级 | 组件 | 作用 | 触发位置 |
|------|------|------|---------|
| 微服务之间 | `TraceIdFilter`（网关）+ `TraceIdInterceptor`（下游服务）+ `FeignTraceIdInterceptor`（Feign 调用） | 生成/传递 `X-Trace-Id`，通过 MDC 让所有日志带 traceId | 网关入口、下游服务拦截器、Feign 请求 |
| 单服务内部 | `WebLogAspect`（AOP 切面） | 自动记录所有 `@RestController` 方法的入参、出参、耗时 | Controller 方法执行前后 |

**日志格式**：

```
2026-06-30 00:24:49.750 [http-nio-8081-exec-3] [7678421356c84f14b8dc1eece60ec8e5] INFO  kb-auth - com.kb.common.trace.WebLogAspect - [7678421356c84f14b8dc1eece60ec8e5] >>> POST /auth/login | args=[{"username":"admin","password":"***"}]
2026-06-30 00:24:51.098 [http-nio-8081-exec-3] [7678421356c84f14b8dc1eece60ec8e5] WARN  kb-auth - com.kb.common.trace.WebLogAspect - [7678421356c84f14b8dc1eece60ec8e5] <<< POST /auth/login | cost=1322ms (SLOW) | result=Result(code=200, message=success, data=LoginResponse(...))
```

**日志元素说明**：

| 元素 | 说明 |
|------|------|
| `[thread]` | 线程名 |
| `[traceId]` | 链路追踪 ID（MDC 填充，跨服务传递） |
| `>>>` | 请求入口：HTTP 方法 + URI + 入参（敏感字段脱敏） |
| `<<<` | 请求出口：HTTP 方法 + URI + 耗时 + 出参（截断超过 1000 字符） |
| `!!!` | 异常：HTTP 方法 + URI + 耗时 + 异常类型 + 异常消息 |
| `(SLOW)` | 慢请求标记（耗时 > 500ms，日志级别提升为 WARN） |
| `password=***` | 敏感字段自动脱敏（password、token、secret、credential、authorization） |

**问题定位流程**（30 秒定位根因）：

```
1. 用户报告"登录失败" → 前端 Network 看到 traceId=7678421356c84f14b8dc1eece60ec8e5
2. SSH 到服务器，执行：
   docker logs --tail 200 kb-auth 2>&1 | grep 7678421356c84f14b8dc1eece60ec8e5
3. 日志立刻显示 >>> 入参 和 <<< 出参（或 !!! 异常），无需猜测
```

**WebLogAspect 自动配置原理**：

- `kb-common` 中的 `TraceIdAutoConfig` 通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 自动注册
- `@ConditionalOnWebApplication(type = SERVLET)` 确保只在 Spring MVC 服务生效（kb-gateway 是 WebFlux，不加载）
- 依赖 `spring-boot-starter-aop`（非 optional，确保 aspectjweaver 传递到下游服务）
- 切入点：`@within(org.springframework.web.bind.annotation.RestController)`，自动覆盖所有 Controller

**关闭 AOP 日志**（紧急情况）：

```bash
# 临时关闭（重启后失效）：在 application.yml 加
# logging:
#   level:
#     com.kb.common.trace.WebLogAspect: OFF

# 永久关闭：在 TraceIdAutoConfig 注释掉 webLogAspect() @Bean
```

```json
{

  "message": "success",
  "data": {

  }

```

```bash
# 所有非白名单接口需要 Authorization 头
```

### 6.3 全文搜索

**两套搜索体系**：
- **用户侧全文搜索**（kb-knowledge + MeiliSearch）：搜索个人知识库的文件/笔记/网页
- **知识引擎文档搜索**（kb-intelligence + MySQL LIKE）：搜索导入的运维文档

```bash
# 基础搜索（MeiliSearch 全文检索）

  -H "Authorization: Bearer $TOKEN"

  -H "Authorization: Bearer $TOKEN"

# 搜索建议（当前占位实现，返回空列表）
curl "https://kb.marschat.online/kb/api/search/suggest?q=Nex" \
  -H "Authorization: Bearer $TOKEN"

# 知识引擎文档搜索（MySQL LIKE）
curl -X POST https://kb.marschat.online/kb/api/intelligence/machine/search \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"Nexus","page":1,"size":20}'
```

> **降级验证**：MeiliSearch 不可用时，搜索接口自动回退 MySQL LIKE，返回结果中 `fallback=true`。

### 9.2 备份

#### 自动备份（推荐）

部署目录下有备份脚本，建议配置 crontab：

```bash
# 编辑 crontab
crontab -e

# 每天凌晨 2:30 执行全量备份
30 2 * * * /root/devtools/mykng/scripts/backup.sh >> /var/log/kb-backup.log 2>&1
```

#### 手动备份

```bash
# 全量备份（MySQL + MongoDB + MinIO 元数据）
bash /root/devtools/mykng/scripts/backup.sh

# 仅备份 MySQL
docker exec kb-mysql mysqldump -uroot -pkb123456 \
  --databases kb_auth kb_file kb_knowledge kb_intelligence \
  --single-transaction --routines --triggers \
  > /root/kb-deploy/backup/mysql/kb_$(date +%Y%m%d_%H%M%S).sql

# 仅备份 MongoDB
docker exec kb-mongodb mongodump --uri="mongodb://kb:kb123456@localhost:27017" \
  --out=/backup/mongodb/$(date +%Y%m%d_%H%M%S)

# 备份 MinIO 数据（使用 mc 客户端）
docker run --rm -v /root/kb-deploy/minio/data:/data \
  -v /root/.mc:/root/.mc minio/mc \
  cp --recursive minio/kb-bucket /backup/minio/$(date +%Y%m%d)
```

### 9.3 恢复

#### MySQL 恢复

```bash
# 1. 停止依赖 MySQL 的服务（避免脏数据）
docker stop kb-gateway kb-auth kb-file kb-knowledge kb-intelligence

# 2. 恢复数据库
docker exec -i kb-mysql mysql -uroot -pkb123456 < /root/kb-deploy/backup/mysql/kb_20260628.sql

# 3. 验证数据
docker exec kb-mysql mysql -uroot -pkb123456 -e "USE kb_auth; SELECT COUNT(*) FROM user;"

# 4. 重启服务
docker start kb-auth kb-file kb-knowledge kb-intelligence kb-gateway

# 5. 健康检查
bash /root/devtools/mykng/scripts/health-check.sh
```

#### MongoDB 恢复

```bash
# 1. 停止 kb-knowledge（避免写入冲突）
docker stop kb-knowledge

# 2. 恢复
docker exec kb-mongodb mongorestore \
  --uri="mongodb://kb:kb123456@localhost:27017" \
  /backup/mongodb/20260628

# 3. 重启
docker start kb-knowledge
```

### 9.5 索引重建（MeiliSearch）

MeiliSearch 共有 3 个用户侧全文搜索索引：`kb_docs`（笔记）、`kb_webpages`（网页）、`kb_files`（文件）。

当前**无手动索引重建 API**，如遇索引不一致：

```bash
# 方案 1：通过 API 触发单条重建（修改资源会自动同步）
curl -X PUT https://kb.marschat.online/kb/api/doc/1 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"原标题"}'

# 方案 2：直接操作 MeiliSearch 清空某索引数据（管理员，谨慎）
curl -X DELETE http://192.168.31.105:7700/indexes/kb_docs/documents \
  -H "Authorization: Bearer <meili-master-key>"

# 方案 3：删除索引（极端情况，会丢失所有该类型索引）
docker exec kb-meilisearch curl -X DELETE http://localhost:7700/indexes/kb_docs
docker exec kb-meilisearch curl -X DELETE http://localhost:7700/indexes/kb_webpages
docker exec kb-meilisearch curl -X DELETE http://localhost:7700/indexes/kb_files
# 删除后重启 kb-knowledge 服务会自动重建索引结构，但需要重新触发数据写入
```

> **知识引擎向量索引（kn_vectors）**：规划中，尚未实现。

### 16.1 错误码对照表

| 错误码 | 含义 | 排查方向 |

| 409 | 资源冲突 | 检查唯一约束（用户名、空间名等） |
| 429 | 限流 | 检查请求频率，降低 QPS |
| 500 | 服务器内部错误 | 查看 `docker logs` 找堆栈 |
| 502 | 网关上游错误 | 检查上游服务健康状态 |
| 503 | 服务不可用 | 检查容器是否启动 |
