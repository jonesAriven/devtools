### 运维数据模型扩展（kb-ops 新增 4 张表）

> kb-ops 模块在原有 8 张表（ops_host、ops_service、ops_change_log、ops_knowledge、ops_conflict、ops_snapshot、ops_operation_log、ops_api_token）基础上，新增 4 张运维数据表，支撑 Port/Credential/Domain/Dependency 四个新 Controller。**注：`ops_change_log` 表对应 `DeploymentRecord` 实体（已存在），此处不重复规划。** 新增列一律以 `ALTER TABLE ADD COLUMN` 方式升级，禁止删表或清空数据。

#### 1. ops_port（端口表）

记录主机上对外开放或内部监听的端口信息，关联主机与服务。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `BIGINT` | 主键，自增 |
| `host_id` | `BIGINT` | 关联主机 ID（ops_host.id） |
| `port` | `INT` | 端口号 |
| `protocol` | `VARCHAR(16)` | 协议（TCP/UDP/HTTP/HTTPS） |
| `service_id` | `BIGINT` | 关联服务 ID（ops_service.id，可空） |
| `purpose` | `VARCHAR(255)` | 用途说明（如"Nginx 入口"、"MySQL 数据库"） |
| `status` | `TINYINT` | 状态（1=监听中、0=未监听、2=异常） |
| `exposed` | `TINYINT` | 是否对外暴露（1=公网可达、0=仅内网） |
| `remark` | `VARCHAR(500)` | 备注 |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |

**索引**：`idx_host (host_id)`、`idx_service (service_id)`、`uk_host_port (host_id, port)`

### 服务间通信

- **同步**：OpenFeign（服务间 API 调用）
- **异步**：RabbitMQ（文件解析完成通知等，后续）
- **服务发现**：无（单机部署，直接 HTTP URL）

### 服务依赖方向（P0 新增）

**严格分层，禁止下层调用上层，禁止同层循环调用：**

```
┌─────────────────────────────────────────────────────────────┐
│                      kb-gateway (:8080)                      │
│              统一入口 + JWT 鉴权 + 静态资源                    │
└──────┬──────────┬──────────────┬────────────┬──────────────┘
       │          │              │            │
       ▼          ▼              ▼            ▼
  ┌─────────┐ ┌─────────┐ ┌───────────┐ ┌─────────┐
  │ kb-auth │ │ kb-file │ │kb-know-   │ │ kb-ops  │
  │ :8081   │ │ :8082   │ │ledge      │ │ :8084   │
  │         │ │         │ │ :8083     │ │         │
  └─────────┘ └────┬────┘ └─────┬─────┘ └────┬────┘
                   │            │            │
                   │  Feign调用  │            │
                   └───────────►│            │
                                │            │
                                │  Feign调用  │
                                └───────────►│
                                              │
                   ┌──────────────────────────┘
                   │  kb-ops 可调用 kb-knowledge（查目录树）
                   │  kb-ops 可调用 kb-auth（验证 Token）
                   ▼
              【下层服务不反向调用上层】
```

**依赖规则：**

| 调用方 → 被调用方 | 允许 | 说明 |
|-------------------|:----:|------|
| kb-gateway → 任意服务 | ✅ | 网关是入口，可调用所有下游 |
| kb-file → kb-knowledge | ✅ | 文件解析完成后通知建索引 |
| kb-ops → kb-knowledge | ✅ | 运维数据关联目录树 |
| kb-ops → kb-auth | ✅ | 验证 API Token |
| kb-knowledge → kb-auth | ✅ | 验证用户身份 |
| kb-knowledge → kb-file | ⚠️ | **写操作禁止**（通过事件解耦）；**读操作允许**（分享详情、回收站、搜索补全文件元数据，需同步调用）|
| kb-auth → 任意服务 | ❌ | **禁止**，auth 是最底层服务 |
| kb-file → kb-ops | ❌ | **禁止**，无业务关联 |
| 同层互相调用 | ❌ | **禁止循环依赖** |

**解耦规则：**
- 当下层需要通知上层时（如 kb-file 解析完成需要 kb-knowledge 建索引），**不直接 Feign 调用**，改为通过 Redis Pub/Sub 或后续 RabbitMQ 事件通知
- 事件格式统一：`{ "event": "file.parsed", "fileId": 123, "content": "...", "timestamp": "..." }`

## P0 优化：统一返回格式 + 全局异常处理

### 统一返回格式（kb-common 模块）

所有服务统一使用 `Result<T>` 包装返回值：

```java
// kb-common: com.kb.common.result.Result
public class Result<T> {
    private int code;        // 200=成功, 400=参数错误, 401=未认证, 403=无权限, 500=服务异常
    private String message;
    private T data;
    private String traceId;  // 链路追踪 ID（P0 新增）

    public static <T> Result<T> success(T data) { ... }
    public static <T> Result<T> error(int code, String message) { ... }
}
```

**前端统一处理：**
```js
// axios 响应拦截器
axios.interceptors.response.use(res => {
  if (res.data.code === 200) return res.data.data;
  if (res.data.code === 401) { /* 跳转登录 */ }
  ElMessage.error(res.data.message);
  return Promise.reject(res.data);
});
```

### 全局异常处理（kb-common 模块）

```java
// kb-common: com.kb.common.exception.GlobalExceptionHandler
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusiness(BusinessException e) {
        log.warn("业务异常: {}", e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(NotLoginException.class)
    public Result<?> handleNotLogin(NotLoginException e) {
        return Result.error(401, "未登录或登录已过期");
    }

    @ExceptionHandler(NoPermissionException.class)
    public Result<?> handleNoPermission(NoPermissionException e) {
        return Result.error(403, "无操作权限");
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<?> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return Result.error(400, "参数校验失败: " + msg);
    }

    @ExceptionHandler(Exception.class)
    public Result<?> handleUnknown(Exception e) {
        log.error("未知异常", e);
        return Result.error(500, "服务内部错误，请稍后重试");
    }
}
```

**自定义异常体系：**
```
RuntimeException
  └── BusinessException (业务异常基类)
        ├── NotLoginException      (401)
        ├── NoPermissionException  (403)
        ├── NotFoundException      (404, 资源不存在)
        ├── ConflictException      (409, 数据冲突)
        └── FileParseException     (422, 文件解析失败)
```

## P0 优化：链路追踪（traceId）

### 实现方案：MDC + 网关注入

**1. 网关生成 traceId 并注入请求头：**

```java
// kb-gateway: TraceIdFilter
@Component
public class TraceIdFilter implements GlobalFilter, Ordered {
    private static final String TRACE_ID = "X-Trace-Id";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String traceId = exchange.getRequest().getHeaders().getFirst(TRACE_ID);
        if (StrUtil.isBlank(traceId)) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        String finalTraceId = traceId;
        return chain.filter(exchange.mutate()
            .request(exchange.getRequest().mutate()
                .header(TRACE_ID, finalTraceId)
                .build())
            .build())
            .then(Mono.fromRunnable(() ->
                exchange.getResponse().getHeaders().add(TRACE_ID, finalTraceId)));
    }

    @Override
    public int getOrder() { return Ordered.HIGHEST_PRECEDENCE; }
}
```

**2. 下游服务从请求头提取 traceId 放入 MDC：**

```java
// kb-common: TraceIdInterceptor
public class TraceIdInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
        String traceId = req.getHeader("X-Trace-Id");
        if (StrUtil.isBlank(traceId)) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        MDC.put("traceId", traceId);
        resp.setHeader("X-Trace-Id", traceId);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse resp, Object handler, Exception ex) {
        MDC.remove("traceId");
    }
}
```

**3. Feign 调用时自动传递 traceId：**

```java
// kb-common: FeignTraceIdInterceptor
@Bean
public RequestInterceptor feignTraceIdInterceptor() {
    return template -> {
        String traceId = MDC.get("traceId");
        if (StrUtil.isNotBlank(traceId)) {
            template.header("X-Trace-Id", traceId);
        }
    };
}
```

**4. Result 返回值携带 traceId（方便前端报错时上报）：**

```java
// 在 GlobalExceptionHandler 中注入
String traceId = MDC.get("traceId");
return Result.error(code, message).withTraceId(traceId);
```


## P1 优化：数据最终一致性方案

### 问题场景

| 场景 | 涉及服务 | 风险 |
|------|---------|------|
| 文件删除后索引未删 | kb-file + kb-knowledge | 搜索命中已删文件 |
| 文件解析成功但索引写入失败 | kb-file + kb-knowledge | 文件存在但搜不到 |
| 运维数据导入但快照未更新 | kb-ops 内部 | 快照数据不准 |
| 分享链接对应文件已删 | kb-knowledge 内部 | 分享打开 404 |

### 方案：事件通知 + 定时补偿（双重保障）

**第一层：实时事件通知（Redis Pub/Sub）**

```java
// 事件发布（kb-file 文件解析完成后）
@Service
public class FileParseService {
    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    public void onParseComplete(Long fileId, String content) {
        KbEvent event = new KbEvent("file.parsed", fileId,
            Map.of("content", content), Instant.now());
        redisTemplate.convertAndSend("kb:events", JSON.toJSONString(event));
    }

    public void onFileDeleted(Long fileId) {
        KbEvent event = new KbEvent("file.deleted", fileId,
            Map.of(), Instant.now());
        redisTemplate.convertAndSend("kb:events", JSON.toJSONString(event));
    }
}

// 事件订阅（kb-knowledge 监听并更新索引）
@Service
public class IndexEventListener {
    @Autowired
    private MeiliSearchService searchService;

    @EventListener
    public void onMessage(String message) {
        KbEvent event = JSON.parseObject(message, KbEvent.class);
        switch (event.getEvent()) {
            case "file.parsed" -> searchService.addIndex("kb_files",
                event.getFileId(), event.getPayload().get("content"));
            case "file.deleted" -> searchService.removeIndex("kb_files",
                event.getFileId());
        }
    }
}
```

**第二层：定时补偿任务（每天 03:00 执行）**

```java
// kb-knowledge: ConsistencyCheckTask
@Service
public class ConsistencyCheckTask {

    /**
     * 每天 03:00 执行数据一致性校验
     * 1. 对比 kb_file 表和 MeiliSearch kb_files 索引，修复差异
     * 2. 对比 share 表和 file 表，标记失效分享
     * 3. 将修复记录写入 operation_log
     */
    @Scheduled(cron = "0 0 3 * * ?")
    public void consistencyCheck() {
        // 1. 索引一致性：MySQL 有但 MeiliSearch 没有的 → 补建索引
        List<Long> missingIndexIds = fileMapper.selectIdsNotInSearchIndex();
        missingIndexIds.forEach(id -> {
            File f = fileMapper.selectById(id);
            searchService.addIndex("kb_files", f.getId(), f.getParsedContent());
            log.info("[补偿] 补建索引 fileId={}", id);
        });

        // 2. 索引清理：MeiliSearch 有但 MySQL 已删除的 → 删索引
        List<Long> orphanIndexIds = searchService.selectOrphanIds("kb_files");
        orphanIndexIds.forEach(id -> {
            searchService.removeIndex("kb_files", id);
            log.info("[补偿] 清理孤儿索引 fileId={}", id);
        });

        // 3. 分享有效性：文件已删但分享还在的 → 标记失效
        shareMapper.markInvalidShares();

        log.info("[一致性检查] 完成，补建 {}，清理 {}，标记失效分享 {}",
            missingIndexIds.size(), orphanIndexIds.size(), ...);
    }
}
```

**补偿任务执行表：**

| 检查项 | 频率 | 异常处理 | 日志 |
|--------|------|---------|------|
| MySQL ↔ MeiliSearch 索引一致性 | 每天 03:00 | 自动补建/清理 | operation_log |
| 分享链接有效性 | 每天 03:00 | 标记失效 | operation_log |
| kb-ops 快照完整性 | 每天 03:00 | 重新统计 | ops_change_log |
| 文件-目录关联完整性 | 每周一 03:00 | 修复孤儿文件 | operation_log |

### v1.1：知识关联能力（待建设）

**目标**：实现类似 Obsidian 的知识网络化能力，让笔记之间形成关联关系。

#### 1. 双向链接

**功能描述**：
- 笔记正文中支持 `[[笔记标题]]` 语法，自动创建双向引用
- 在笔记详情页底部展示"反向链接"列表（引用了当前笔记的所有笔记）
- 支持悬停预览链接目标笔记摘要

**数据模型变更**（需以 ALTER TABLE 升级方式）：
```sql
-- 笔记关联关系表（新增）
CREATE TABLE IF NOT EXISTS doc_link (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    source_doc_id BIGINT NOT NULL COMMENT '来源笔记ID',
    target_doc_id BIGINT NOT NULL COMMENT '目标笔记ID',
    link_text VARCHAR(255) COMMENT '链接显示文本',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_source (source_doc_id),
    INDEX idx_target (target_doc_id),
    UNIQUE KEY uk_link (source_doc_id, target_doc_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='笔记双向链接关系';
```

**核心 API**：
- `GET /kb/api/doc/{id}/backlinks` — 获取反向链接列表
- `GET /kb/api/doc/{id}/forward-links` — 获取正向链接列表

**实现要点**：
- 笔记保存时解析 `[[xxx]]` 语法，更新 `doc_link` 表
- 反向链接查询走索引，O(1) 复杂度
- 链接目标不存在时，前端支持"点击创建"

#### 2. 图谱视图

**功能描述**：
- 全局知识图谱：可视化所有笔记的关联关系网络
- 局部图谱：以当前笔记为中心，展示 N 度关联网络
- 节点大小按链接数排序，颜色按空间/标签区分
- 支持拖拽、缩放、点击跳转

**前端选型**：Vue3 + vis-network 或 cytoscape.js

**核心 API**：
- `GET /kb/api/graph/full?depth=2` — 全局图谱（限制深度）
- `GET /kb/api/graph/node/{docId}?depth=2` — 局部图谱

**性能考量**：
- 图谱节点超过 500 个时需分页/聚类
- 前端使用 Canvas 渲染（非 SVG）避免 DOM 性能问题

### v1.3：RAG 检索增强 — 向量索引与语义搜索（待建设）

**目标**：突破关键词字面匹配的限制，实现语义级检索能力。

#### 背景与痛点

当前 MeiliSearch 全文搜索存在以下局限：
- 搜"部署"搜不到标题为"上线流程"的文档
- 搜"性能优化"搜不到内容为"JVM 调优"的笔记
- 无法跨语言匹配（中文搜英文文档）
- 无近义词/概念匹配能力

#### 技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 向量数据库 | **MeiliSearch 1.x Hybrid Search** | 复用现有组件，无需新增 |
| 嵌入模型 | **bge-small-zh-v1.5（ONNX）** | 本地推理，~100MB，CPU 可跑 |
| 向量维度 | 512 | bge-small 标准输出 |
| LLM | 暂不接入（v1.5 再做） | 本期仅做检索 |

#### 架构设计

```
写入流程：
  文档/笔记/网页保存
      ↓
  bge-small-zh 生成 embedding（512维向量）
      ↓
  存入 MeiliSearch _vectors 字段

检索流程：
  用户输入查询词
      ↓
  bge-small-zh 生成查询向量
      ↓
  MeiliSearch 向量检索 + 关键词检索（Hybrid）
      ↓
  融合排序返回结果
```

#### 数据模型变更

MeiliSearch 索引新增 `_vectors` 字段：
```json
{
  "id": "15",
  "title": "JVM 调优实践",
  "content": "...",
  "_vectors": {
    "default": [0.0123, -0.0456, ... 512个浮点数]
  }
}
```

#### 实施步骤

1. **集成嵌入模型**：引入 ONNX Runtime + bge-small-zh 模型到 kb-knowledge 服务
2. **改造 SearchIndexService**：写入文档时同步生成 embedding 存入 `_vectors`
3. **改造搜索接口**：新增 `mode=semantic` 参数，调用 MeiliSearch 向量检索
4. **前端适配**：搜索页新增"语义搜索"开关
5. **补偿任务**：ConsistencyCheckTask 增加向量重建逻辑
6. **历史数据迁移**：对已存在的文档批量生成 embedding

#### 预期效果
- 语义搜索：搜"部署"命中"上线流程"
- 跨语言检索：中文搜英文文档
- 近义词匹配：搜"性能优化"命中"调优"

### v1.4：RAG 检索增强 — 混合搜索（待建设）

**目标**：融合关键词搜索与语义搜索，提供最优检索质量。

#### 功能描述
- Hybrid Search：同时执行关键词检索和向量检索，结果融合排序
- 相关性调优：支持配置关键词权重和向量权重

```
GET /kb/api/search?q=&mode=hybrid&kwWeight=0.4&vecWeight=0.6
```

- 前端默认使用 hybrid 模式，保留切换为 keyword/semantic 的选项

### v1.5：AI 问答助手（待建设）

**目标**：基于私有知识库的智能问答，实现"问知识库"而非"搜知识库"的交互升级。

#### 功能描述
- 用户自然语言提问 → 向量检索 Top K 相关片段 → LLM 基于片段生成答案
- 答案附带引用来源（文档链接 + 高亮片段）
- 支持多轮对话，上下文记忆
- 跨知识源聚合：回答同时引用文件、笔记、网页、运维记录

#### 技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| LLM | **Qwen2-1.5B-Q4（本地）** | 已规划，按需启动，~1.5GB 内存 |
| 备选 | 通义千问在线 API | 资源不足时降级方案 |
| 向量检索 | MeiliSearch（v1.3 已建设） | 复用已有索引 |
| Prompt 工程 | RAG 模板 | 拼接 Top K 片段 + 系统提示 |

#### 架构设计

```
用户提问
    ↓
[1] 向量检索：MeiliSearch 召回 Top 5 相关片段
    ↓
[2] Prompt 拼接：系统提示 + 检索片段 + 用户问题
    ↓
[3] LLM 生成：Qwen2 基于上下文生成答案
    ↓
[4] 引用溯源：标注答案来源文档 + 高亮片段
    ↓
返回答案 + 引用列表
```

#### API 设计
```
POST /kb/api/ai/chat
{
  "question": "如何部署应用到生产环境？",
  "history": [...]
}
```

#### 实现要点
- 文档分块：长文档按段落切分（每块 500 字，重叠 100 字）
- 上下文窗口：Top 5 片段，总 token 控制在 2000 以内
- 引用溯源：记录每个片段的 docId + 段落位置
- 安全防护：敏感信息（账密）不进入 LLM 上下文

#### 资源评估
| 组件 | 内存占用 | 启动方式 |
|------|---------|---------|
| Qwen2-1.5B-Q4 | ~1.5GB | 按需启动 |
| bge-small-zh（v1.3 已有） | ~300MB | 常驻 |
| **新增总计** | **~1.5GB** | 需确认 VM 余量 |
