## 二、关键配置点说明（重点）

> **本节是测试的前置约束**。所有测试用例必须基于以下配置正确性，否则测试结果无效。

### 2.1 上下文路径 `KB_CONTEXT=/kb`（核心配置点）

**设计原则**（详见 [知识库部署方案_20260627.md](知识库部署方案_20260627.md) 第 66 行）：
> `KB_CONTEXT=/kb` **一处配置，前后端 + Nginx 同步**

#### 配置位置（4 处必须一致）

| 序号 | 位置 | 文件路径 | 配置项 | 当前值 |
|------|------|---------|--------|--------|
| ① | 部署环境变量 | `mykng/.env` | `KB_CONTEXT=/kb` | `/kb` ✅ |
| ② | 前端构建变量 | `kb-web/.env` 与 `kb-web/.env.production` | `VITE_CONTEXT_PATH=/kb` | `/kb` ✅ |
| ③ | 网关路由配置 | `kb-gateway/src/main/resources/application.yml` | `${KB_CONTEXT:/kb}/api/**` + `StripPrefix=2` | `/kb` ✅ |
| ④ | Nginx 反代配置 | 腾讯云2号 `/etc/nginx/sites-available/kb` 与项目 `nginx/kb.marschat.online.conf` | `location /kb/api/` → `proxy_pass .../kb/api/` | `/kb` ✅ |

#### 路径流转链路（关键理解点）

```
公网请求                     网关                          后端服务
─────────────────────────────────────────────────────────────────────
GET https://kb.marschat.online/kb/api/user/profile
                              │
                              ▼
  Nginx 反代：location /kb/api/ → proxy_pass http://100.93.36.113:8090/kb/api/
                              │
                              ▼
  kb-gateway 收到：/kb/api/user/profile
    ├ Path 断言：${KB_CONTEXT}/api/user/** 匹配
    ├ StripPrefix=2 剥离 /kb/api 两段
    └ 转发到 kb-auth:8081/user/profile
                              │
                              ▼
  kb-auth 收到：/user/profile（已剥离上下文）
    └ UserController.@GetMapping("/profile") 处理
```

#### 公网路径格式

```
http(s)://{域名或网关地址}{KB_CONTEXT}/api/{module}/{action}
                    │              │       │      │
                    │              │       │      └ Controller @RequestMapping 定义的路径
                    │              │       └ /auth / /user / /file / /doc / /ops/host 等
                    │              └ 固定标识，不可修改
                    └ /kb（由 KB_CONTEXT 控制，修改后四处同步）
```

#### 修改 KB_CONTEXT 时的同步检查清单

> 测试用例 L4-CTX-001 验证此项。

修改上下文路径为 `/mykb` 时，必须同步修改：

- [ ] `mykng/.env` → `KB_CONTEXT=/mykb`
- [ ] `kb-web/.env` 与 `.env.production` → `VITE_CONTEXT_PATH=/mykb`
- [ ] 重新构建前端 `pnpm build`，重新部署 dist
- [ ] 重新部署 `docker compose up -d kb-gateway`（网关读取新环境变量）
- [ ] Nginx 配置 `location /mykb/api/` 与 `location /mykb/` 与 `location /mykb/s/`
- [ ] `nginx -t && nginx -s reload`

### 2.2 鉴权机制

| 配置项 | 位置 | 说明 |
|--------|------|------|
| JWT 签名密钥 | `mykng/.env` → `JWT_SECRET` | 前后端、网关共用 |
| Access Token 有效期 | kb-auth `application.yml` | 15 分钟（900000ms） |
| Refresh Token 有效期 | kb-auth `application.yml` | 7 天（604800000ms） |
| 网关白名单 | kb-gateway `application.yml` | `/kb/api/auth/login`、`/kb/api/auth/refresh`、`/kb/api/share/verify/**` |

### 2.3 测试澄清：之前的测试是否带上下文路径？

**澄清结论**：是的，已带。

`tests/test_full_api.py` 第 14 行 `BASE_URL = "https://kb.marschat.online"`，所有测试调用路径都是 `/kb/api/...`（见第 114-147 行，如 `test_api("auth", "用户登录", "POST", "/kb/api/auth/login", ...)`）。

之前出现"测试失败率高"的根因**不是漏带上下文路径**，而是：

1. **测试脚本本身的路径错误**（与接口规范不一致）：
   - 调用 `/kb/api/token/list`，但规范是 `/kb/api/token`（无 /list）
   - 调用 `/kb/api/file/init`、`/kb/api/file/search`，但规范无此端点
   - 调用 `/kb/api/file/parse/status?fileId=1`，但规范是 `/kb/api/file/{id}/parse-status`
   - 调用 `/kb/api/bucket/test-bucket`，但规范是 `/kb/api/bucket/{id}/stats`
   - 调用 18 个 kb-ops 的 port/credential/domain/dependency/change 接口，但前端 `kb-web/src/api/ops.ts` 完全不调用这些接口（测试脚本编造；其中 port/credential/domain/dependency 四类接口已于接口规范清单 v2.2 正式新增，change 接口仍属编造）
2. **前后端真实不一致**（需修复）：
   - 前端调 `GET /auth/me`，后端无此端点
   - 前端调 `GET /folder/{id}`、`GET /space/{id}`，后端无此端点
   - 前端调 `POST /file/chunk/init`、`POST /file/chunk/upload`、`POST /file/chunk/complete`，后端只有 `/file/upload`、`/file/merge`
   - 前端调 `DELETE /trash/empty`，后端无此端点
   - 前端调 `POST /tag/resource`，后端是 `POST /tag/bind`
3. **真实 bug**：`POST /auth/refresh` 因 `refresh_token` 表无唯一约束导致 `TooManyResultsException`

本测试方案将基于接口规范清单（v2.2，116 接口）重新设计测试用例，并明确标注前后端不一致项。

## 三、测试策略（测试金字塔）

按业界测试金字塔，从底层到顶层分为 5 层：

```
                    ┌──────────────────────┐
                    │  L5 非功能测试        │  安全/性能/兼容性（本方案含基础项）
                    └──────────────────────┘
                  ┌──────────────────────────┐
                  │  L4 全量功能测试          │  Python + requests 覆盖 116 API
                  └──────────────────────────┘
                ┌──────────────────────────────┐
                │  L3 E2E 测试                 │  Playwright 覆盖 13 页面 + 关键流程
                └──────────────────────────────┘
              ┌──────────────────────────────────┐
              │  L2 集成测试                      │  Spring Boot Test + 真实容器
              └──────────────────────────────────┘
            ┌──────────────────────────────────────┐
            │  L1 单元测试                          │  JUnit 5 + Mockito
            └──────────────────────────────────────┘
```

| 层级 | 工具 | 覆盖范围 | 执行频率 | 责任人 |
|------|------|---------|---------|--------|
| L1 单元 | JUnit 5 + Mockito | Service 层业务逻辑、工具类、异常处理 | 每次提交 | 开发 |
| L2 集成 | Spring Boot Test + Testcontainers | Controller + Mapper + 真实数据库 | 每日构建 | 开发 |
| L3 E2E | Playwright (Python) | 13 前端页面 + 5 个关键业务流程 | 每次发版 | 测试 |
| L4 全量功能 | Python + urllib/requests | 116 个 API 契约测试 | 每次发版 | 测试 |
| L5 非功能 | curl + 浏览器 + 压测工具 | 鉴权、CORS、错误码、性能基线 | 每次发版 | 测试 |

### 3.1 通过准则

| 层级 | 通过标准 |
|------|---------|
| L1 单元 | 覆盖率 ≥ 70%（Service 层），所有用例通过 |
| L2 集成 | 关键模块（auth/file/knowledge/ops）核心流程通过 |
| L3 E2E | 13 页面全部可访问，5 个关键业务流程闭环 |
| L4 全量功能 | 116 个 API 中，前后端一致且后端实现的接口 100% 通过；前后端不一致项明确标注为 KNOWN_ISSUE |
| L5 非功能 | 鉴权、CORS、错误码符合规范；登录接口 P95 < 500ms |

### 7.3 10 大业务流程测试用例（复用 test_functional.py）

> 以下 10 大业务流程在 L4 全量功能测试（`tests/functional/test_functional.py`）中编排，端到端验证关键链路闭环。前 5 项与 L3 E2E 的 L3-FLOW-001~005 对应，后 5 项为 L4 补充流程。

| 流程 ID | 业务流程 | 涉及接口（节选） | 预期 |
|---------|---------|------------------|------|
| FLOW-01 | 登录认证闭环 | POST /auth/login → GET /user/profile → POST /auth/refresh → POST /auth/logout | 全程无 401，token 自动刷新 |
| FLOW-02 | 知识空间-文档管理 | POST /space → GET /folder/tree → POST /doc → PUT /doc/{id} → GET /version/list → DELETE /doc/{id} → POST /trash/restore | 文档生命周期完整 |
| FLOW-03 | 文件上传-搜索 | POST /file/upload → POST /file/merge → GET /file/{id}/parse-status → GET /search?q= → GET /file/{id}/download | 索引建立，下载链接有效 |
| FLOW-04 | 分享-访问 | POST /share → GET /share/verify/{code}（带提取码）→ GET /share/detail/{code} | 分享可公开访问 |
| FLOW-05 | 运维看板-矛盾检测 | GET /ops/dashboard → POST /ops/host → GET /ops/service/list → POST /ops/conflict/detect → GET /ops/conflict/list | 看板数据正确，冲突检测有效 |
| FLOW-06 | 标签-筛选文档 | POST /tag → POST /tag/bind → GET /search?tagId={id} → DELETE /tag/unbind → DELETE /tag/{id} | 标签绑定后可按标签检索 |
| FLOW-07 | 回收站-恢复-彻底删除 | DELETE /doc/{id} → GET /trash/list → POST /trash/restore/{type}/{id} → DELETE /trash/{type}/{id} | 逻辑删除 → 恢复 → 物理删除链路通 |
| FLOW-08 | 端口-凭据管理（新增） | POST /ops/port → GET /ops/port/list → POST /ops/credential → GET /ops/credential/{id}?revealPassword=false → DELETE /ops/credential/{id} | 端口/凭据 CRUD 闭环，密码默认不返回 |
| FLOW-09 | 域名-到期管理（新增） | POST /ops/domain → GET /ops/domain/list?status=2 → PUT /ops/domain/{id} → DELETE /ops/domain/{id} | 域名 CRUD 与即将过期筛选有效 |
| FLOW-10 | 依赖关系-拓扑（新增） | POST /ops/dependency → GET /ops/dependency/list?serviceId={id} → DELETE /ops/dependency/{id} | 依赖关系录入与按服务查询有效 |

> **执行说明**：10 大业务流程统一在 `tests/functional/test_functional.py` 中实现，发版前必跑；流程编号 FLOW-01~05 与 L3 E2E（L3-FLOW-001~005）语义对齐，FLOW-06~10 为 L4 独有补充流程。
