# 架构反思：为什么剥离一个模块这么费时费力？

> 日期：2026-07-03
> 触发事件：kb-ops 模块从 mykng 剥离为独立项目
> 核心问题：理想架构下"模块像插件一样可插拔"，为何本次剥离如此复杂？

## 一、本次剥离的实际工作量

剥离 kb-ops 一个模块，实际涉及的工作清单：

| 类别 | 工作项 | 文件数 | 耗时占比 |
|------|--------|--------|----------|
| 代码删除 | 删除 kb-ops 目录（82个Java文件、13个Controller） | 82 | 5% |
| 构建配置 | pom.xml 移除模块注册 | 1 | 2% |
| 网关路由 | application.yml + 3个环境配置（dev/prod/uat/staging） | 4 | 5% |
| 编排配置 | docker-compose.yml 移除服务块 | 1 | 3% |
| CI/CD 配置 | ci.yml / cd.yml / dependabot.yml / sonar-project.properties | 4 | 8% |
| 脚本清理 | build/start/restart/rollback/deploy/health-check 等 15 个脚本 | 15 | 12% |
| 测试清理 | test_full_api.ps1 / e2e-test.ps1 | 2 | 3% |
| SQL 清理 | 04-kb-ops.sql 删除 + 01-create-databases.sql 调整 | 2 | 2% |
| 死代码清理 | kb-common 中 KbEvent.java 的 OPS_IMPORTED/OPS_CONFLICT 常量 | 1 | 2% |
| 数据迁移 | OperationLog 从 kb-ops 迁移到 kb-auth（@Async/@EnableAsync） | 5 | 8% |
| 独立项目改造 | 内联 9 个 kb-common 类 + 改造 pom.xml + 调整配置 | 15 | 15% |
| 文档更新 | 归档 1 个 + 更新 10 个核心文档 + 创建 1 个方案文档 | 12 | 20% |
| 基础设施 | 停止 Docker 容器 + 配置双层 Nginx + 部署 portal | - | 15% |
| **合计** | | **~140 项** | **100%** |

**关键发现**：真正"删除模块代码"只占 5% 的工作量，95% 的工作量花在"处理散落在各处的配置、脚本、文档、依赖关系"上。

## 二、五大痛点根因分析

### 痛点 1：公共库共享导致编译时耦合

**现象**：kb-ops 依赖 kb-common 的 9 个类（Result / PageResult / BusinessException / NotFoundException / GlobalExceptionHandler / TraceIdInterceptor / FeignTraceIdInterceptor / WebLogAspect / TraceIdAutoConfig）。剥离为独立项目时，必须把这 9 个类的源码全部内联复制。

**根因**：
```
当前架构：模块 → 编译时依赖 → kb-common（共享源码）
理想架构：模块 → 运行时依赖 → kb-common.jar（独立制品）
```

kb-common 是以 **源码模块** 形式存在于 mykng 项目中，所有微服务通过 Maven 模块依赖直接引用源码。这导致：
- 任何模块剥离时，必须带上 kb-common 的源码副本
- kb-common 的修改会同时影响所有模块（耦合放大器）
- 无法独立发布 kb-common 的版本

**对比业界**：Spring Cloud 生态中，公共库（如 spring-cloud-commons）以 **独立 jar 包** 形式发布到 Maven 仓库，各服务通过 `<dependency>` 引用特定版本。剥离服务时只需保留 jar 依赖，无需复制源码。

### 痛点 2：配置散落在 7+ 个位置

**现象**：kb-ops 的"存在"被硬编码在至少 7 类配置文件中：

| 配置位置 | 文件 | 引用方式 |
|----------|------|----------|
| 父 POM | kb-parent/pom.xml | `<module>../kb-ops</module>` |
| 网关路由 | kb-gateway/application*.yml（4个） | `id: kb-ops` + `uri: lb://kb-ops` |
| 编排文件 | docker-compose.yml | `kb-ops:` 服务块 + 环境变量 |
| CI 流水线 | ci.yml | 服务列表循环 |
| CD 流水线 | cd.yml | 镜像构建/推送/部署循环 |
| 依赖更新 | dependabot.yml | maven + docker 两个 ecosystem 块 |
| 质量扫描 | sonar-project.properties | `sonar.sources` 列表 |
| 部署脚本 | 15 个 .sh/.ps1 脚本 | 服务名硬编码在数组里 |
| 测试脚本 | 2 个测试文件 | kb-ops 测试段落 |
| SQL 初始化 | 2 个 SQL 文件 | 建库 + 建表 |

**根因**：**没有模块注册中心**。每个配置文件独立维护自己的"模块清单"，彼此不同步。添加/移除模块时，必须人工遍历所有配置点逐一修改，极易遗漏。

**对比业界**：
- Kubernetes 生态：模块以 Helm Chart 或 Kustomize 形式存在，添加/移除只需 `helm install/uninstall`
- Spring Cloud：服务通过服务发现（Nacos/Eureka）自动注册，网关路由可动态配置
- 现代微服务：模块清单集中在 `service-registry.yml`，CI/CD/脚本/监控全部从该清单生成

### 痛点 3：Maven 父子工程结构的固有限制

**现象**：所有模块继承 kb-parent，依赖版本由 kb-parent 的 `dependencyManagement` 统一管理。剥离 kb-ops 为独立项目时，必须：
1. 把 parent 从 `kb-parent` 改为 `spring-boot-starter-parent`
2. 为所有依赖重新指定版本号（MyBatis-Plus 3.5.6 / Hutool 5.8.27 / Cucumber 7.18.1 ...）
3. 重新配置 Nexus 私服仓库

**根因**：Maven 的父子 POM 结构是 **编译时强绑定**。子模块无法"继承一部分、独立一部分"。要么完全留在父工程内，要么完全独立并自建版本管理。

**对比业界**：
- Gradle 的 `platform` / `BOM` 机制：可独立引用版本平台，不强制父子结构
- Spring Boot 的 `dependencyManagement` 通过 `spring-boot-dependencies` BOM 导入，而非父子继承

### 痛点 4：服务间 Feign 直接调用

**现象**：kb-ops 通过 Feign 直接调用 kb-auth 验证 Token，通过 Feign 调用 kb-intelligence 同步知识。剥离后这些调用关系需要调整或标注为可选。

**根因**：服务间通过 **Feign 直接依赖** 而非通过 **网关统一入口** 通信。这导致：
- 服务间形成网状依赖（kb-ops → kb-auth, kb-ops → kb-intelligence）
- 剥离时需要梳理所有调用链路
- 无法独立测试单个服务

**对比业界**：
- Service Mesh（Istio/Linkerd）：服务间通信由 Sidecar 代理，应用层无感知
- API Gateway 模式：所有跨服务调用通过网关，服务间无直接依赖
- 事件驱动：服务间通过消息队列（Kafka/RabbitMQ）解耦，生产者不关心消费者是否存在

### 痛点 5：文档与代码双向不同步

**现象**：10+ 个文档提到 kb-ops（README、PRD、部署方案、运维手册、API设计、数据库设计、接口规范清单、使用说明书等）。剥离后必须逐一更新。

**根因**：**文档是手动维护的**，与代码没有自动同步机制。每次架构变更，文档更新完全依赖人工记忆和纪律，极易遗漏。

**对比业界**：
- OpenAPI/Swagger：API 文档从代码注解自动生成
- Structurizr：架构图从代码模型自动渲染
- C4 Model + adr-tools：架构决策记录与代码同仓库，变更时强制更新

## 三、根本矛盾：这是"微服务"还是"分布式单体"？

当前 mykng 的架构本质上是 **分布式单体（Distributed Monolith）**：

| 特征 | 真正的微服务 | mykng 现状 |
|------|-------------|-----------|
| 独立部署 | ✅ 可独立部署 | ⚠️ 共享 kb-common，独立部署需内联源码 |
| 独立技术栈 | ✅ 可用不同语言/框架 | ❌ 统一 Java 21 + Spring Boot 3.2 |
| 数据自治 | ✅ 每服务独享数据库 | ⚠️ 共享 MySQL 实例，分库但同实例 |
| 松耦合 | ✅ 通过 API/事件通信 | ❌ Feign 直接调用 + 共享 kb-common |
| 独立版本 | ✅ 各服务独立版本号 | ❌ 统一 kb-parent 1.0.0 |
| 团队自治 | ✅ 不同团队负责不同服务 | ❌ 单人全栈开发 |

**结论**：mykng 享受了微服务的"复杂性"（网络调用、分布式事务、运维成本），却没有享受微服务的"独立性"（可插拔、独立部署、松耦合）。这是本次剥离费时费力的根本原因。

## 四、改进路线图

### 短期改进（1-2 周，低成本）

#### 1. 模块清单文件（module-registry.yml）
在项目根目录创建统一的模块清单，所有脚本/CI/CD 从该文件读取模块列表：

```yaml
# module-registry.yml
modules:
  - name: kb-gateway
    type: service
    port: 8080
    context: /kb
    health: /actuator/health
  - name: kb-auth
    type: service
    port: 8081
    dependencies: [mysql, redis]
  # ... 添加/移除模块只需改这里
```

脚本改为：
```bash
MODULES=$(yq '.modules[].name' module-registry.yml)
for svc in $MODULES; do docker build $svc; done
```

**收益**：添加/移除模块从"改 15 个文件"变成"改 1 个文件"。

#### 2. 公共库独立打包发布
把 kb-common 构建为独立 jar，发布到 Nexus 私服：

```xml
<!-- 各服务引用方式从源码依赖改为 jar 依赖 -->
<dependency>
    <groupId>com.kb</groupId>
    <artifactId>kb-common</artifactId>
    <version>1.1.0</version>  <!-- 引用特定版本 -->
</dependency>
```

**收益**：剥离服务时只需保留 jar 依赖，无需复制源码。

### 中期改进（1 个月，中等成本）

#### 3. 网关路由动态化
网关路由从配置文件改为从数据库/Nacos 动态加载：

```yaml
# 路由配置存数据库，网关启动时加载，支持热更新
spring:
  cloud:
    gateway:
      routes:
        - id: ${route.id}
          uri: lb://${route.service-name}
          predicates: ${route.predicates}
```

**收益**：添加/移除模块只需在数据库增删一条路由记录，网关自动生效。

#### 4. 服务间调用通过网关
Feign 调用从直连改为统一走网关：

```java
// 当前：直连 kb-auth
@FeignClient(name = "kb-auth")

// 改进：走网关
@FeignClient(name = "kb-gateway", url = "${gateway.url}/kb/api/auth")
```

**收益**：服务间无直接依赖，剥离时不影响其他服务。

### 长期改进（2-3 个月，高成本）

#### 5. 事件驱动解耦
引入消息队列（Redis Streams / RabbitMQ），服务间通过事件通信：

```
当前：kb-file → Feign → kb-knowledge（同步调用）
改进：kb-file → 发布事件 → MQ → kb-knowledge（异步消费）
```

**收益**：生产者不关心消费者是否存在，真正可插拔。

#### 6. 容器化编排统一
用 Docker Compose profiles 或 Kubernetes 实现模块编排：

```yaml
# docker-compose.yml
services:
  kb-ops:
    profiles: ["ops"]  # 只在指定 profile 时启动
```

```bash
docker compose --profile ops up    # 启动含 kb-ops
docker compose up                   # 启动不含 kb-ops
```

**收益**：模块启停通过 profile 切换，无需修改编排文件。

## 五、总结

| 维度 | 当前状态 | 理想状态 | 差距 |
|------|---------|---------|------|
| 公共库 | 源码共享 | jar 包依赖 | 短期可改进 |
| 模块注册 | 散落 15+ 文件 | 统一清单文件 | 短期可改进 |
| 版本管理 | 父 POM 强绑定 | BOM 平台引用 | 中期可改进 |
| 服务通信 | Feign 直连 | 网关/MQ 解耦 | 中长期可改进 |
| 文档同步 | 手动维护 | 代码自动生成 | 长期可改进 |

**核心反思**：本次剥离费时费力，**不是单一原因，而是架构设计层面的系统性问题**。kb-ops 在代码层面只占 5% 的工作量，95% 的工作量花在处理"散落的配置、共享的依赖、耦合的通信、手动维护的文档"上。

如果要做到"模块像插件一样可插拔"，需要从 **公共库独立化 + 模块清单统一 + 服务通信解耦** 三个维度同时改进。短期建议优先落地"模块清单文件"和"公共库独立打包"，这两个改进成本低但收益显著。
