## 一、评估背景与方法

### 1.1 评估目的

在 2026-07-03 报告（聚焦现有功能健全性 + 交互体验 + 问题清单）的基础上，本次评估聚焦三件事：

1. **对标业界**：梳理 Notion / Confluence / Obsidian / Outline / Wiki.js / BookStack / 飞书 / 语雀 / Slite / Guru / Document360 / Glean 等主流知识库的功能特性，归纳"业界都有的功能"
2. **识别差距**：对比 mykng 现状，找出可取长补短的建设方向
3. **插件化架构**：设计可插拔的插件化架构，让新功能像插件一样可安装/卸载/启用/禁用，方便后续功能扩展、模块上下线

### 1.2 评估方法

| 维度 | 方法 |
|------|------|
| 业界调研 | Web 搜索 + 资料阅读（覆盖国内外 12+ 主流知识库产品） |
| 现状对比 | 基于 2026-07-03 报告的功能清单 + 代码现状 |
| 架构设计 | 基于"架构反思"和"重构方案"的可插拔六大支柱，聚焦"功能插件化" |
| 插件规范 | 定义插件契约、生命周期、注册机制、依赖管理 |

## 三、mykng 现状对标分析

### 3.1 mykng 独特优势（继续保持）

| 优势 | 说明 | 业界对比 |
|------|------|---------|
| 私有化部署 | 数据自主可控，不依赖云厂商 | 优于 Notion/Confluence/飞书等 SaaS |
| 知识引擎实体识别 | 运维场景独特价值（主机/服务/端口/凭据/域名/命令/时间线） | 业界独有（Obsidian/Notion 无） |
| 网页收藏 + 离线阅读 | 抓取网页内容本地化存储 | 优于 Notion（Notion 无网页收藏） |
| 多格式笔记 + 双向链接 | 类 Obsidian 的笔记体验 | 与 Obsidian 同级 |
| 搜索性能 | MeiliSearch 响应 46.8ms | 优于多数 SaaS 产品 |
| 上下文路径部署 | 支持 `/kb` 上下文路径 | 符合企业部署规范 |

### 3.3 定位建议

基于业界对比，建议明确 mykng 定位为：

> **私有化部署的个人/小团队知识库 + 运维知识引擎 + AI 智能问答**

差异化竞争点：
1. **私有化**（vs Notion/Confluence/飞书等 SaaS）
2. **知识引擎**（vs Obsidian/Outline 等纯笔记工具）
3. **AI 智能问答**（vs 传统 Wiki 如 BookStack/DokuWiki）

### 5.2 插件契约（Plugin Contract）

每个插件必须包含以下组件（缺一不可，否则视为不完整插件）：

```yaml
# 插件清单示例（plugin-manifest.yml）
plugin:
  id: plugin-rbac                    # 唯一标识（与 module-registry.yml 的 name 对应）
  name: RBAC 权限插件
  version: 1.0.0
  type: service                      # service / frontend / mixed
  priority: P0                       # P0 / P1 / P2 / P3
  removable: false                   # 核心插件不可移除
  enabled-by-default: true            # 默认启用

  # 依赖声明
  dependencies:
    modules: [kb-auth]               # 依赖的微服务模块
    plugins: []                      # 依赖的其他插件
    infra: [mysql, redis]            # 依赖的基础设施

  # 后端组件
  backend:
    module: kb-auth                  # 所属后端模块
    controllers:
      - com.kb.auth.controller.RoleController
      - com.kb.auth.controller.PermissionController
    entities:
      - com.kb.auth.entity.Role
      - com.kb.auth.entity.Permission
    services:
      - com.kb.auth.service.RoleService
    config-prefix: kb.security.rbac  # 配置前缀

  # 前端组件
  frontend:
    routes:                          # 前端路由
      - path: /system/role
        view: views/system/RoleManageView
```

#### 5.7.3 插件发现机制

```java
package com.kb.common.plugin;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * 插件注册中心
 * <p>
 * 启动时扫描所有 KbPlugin 实现，注册到注册中心。
 * 根据 plugin_status 表的状态决定是否激活。
 */
@Component
public class PluginRegistry {

    private final Map<String, KbPlugin> plugins = new ConcurrentHashMap<>();

    @Autowired
    private PluginStatusMapper pluginStatusMapper;

    /** 注册插件（Spring 启动时自动调用） */
    public void register(KbPlugin plugin) {
        plugins.put(plugin.getId(), plugin);
    }

    /** 启用插件 */
    public void enable(String pluginId) {
        KbPlugin plugin = plugins.get(pluginId);
        if (plugin == null) throw new IllegalArgumentException("插件不存在: " + pluginId);
        // 检查依赖
        checkDependencies(pluginId);
        // 回调
        plugin.onEnable(createContext());
        // 更新状态
        pluginStatusMapper.updateStatus(pluginId, "enabled");
    }

    /** 禁用插件 */
    public void disable(String pluginId) {
        KbPlugin plugin = plugins.get(pluginId);
        if (plugin != null) {
            plugin.onDisable(createContext());
        }
        pluginStatusMapper.updateStatus(pluginId, "disabled");
    }

    /** 获取已启用的插件 */
    public List<KbPlugin> getEnabledPlugins() {
        return plugins.values().stream()
            .filter(p -> "enabled".equals(pluginStatusMapper.getStatus(p.getId())))
            .toList();
    }
}
```

### 7.1 核心发现

1. **mykng 在"私有化 + 知识引擎"维度有独特优势**，与 Notion/Confluence/飞书等 SaaS 差异化竞争
2. **与业界差距集中在"协作 + AI + 集成"三个维度**，需通过插件化方式补齐
3. **现有架构是"分布式单体"**（见 [架构反思](file:///D:/huliang/java/ideaworkspace/devtools/mykng/docs/架构反思_模块剥离痛点分析_20260703.md)），需先建设可插拔架构再叠加新功能
4. **业界 AI 趋势明显**（Slite/Guru/Notion AI），mykng 应布局 LLM 智能问答插件
5. **插件化是规模化扩展的关键**，避免功能堆砌导致系统臃肿

### 7.2 建设优先级建议

1. **先建可插拔架构基石**（module-registry.yml + 插件契约 + SPI），这是所有后续插件的前提
2. **再建核心必建插件**（RBAC + 用户管理 + 安全 + 分片上传），补齐 P0 缺失
3. **后建体验提升插件**（评论通知 + 图谱 + 状态机），提升协作能力
4. **最后建智能化插件**（LLM 问答 + 摘要 + 自维护），拥抱 AI 趋势

### 7.3 风险提示

| 风险 | 应对 |
|------|------|
| 过度设计 | 每个插件独立交付价值，避免一次性建设过多 |
| 向后兼容 | 新插件不能破坏现有功能，通过配置开关控制 |
| 数据安全 | 插件数据库迁移必须兼容已有数据（ALTER TABLE 方式） |
| AI 成本 | LLM 插件需配置 API 限额和成本监控 |
| 依赖耦合 | 严格遵循插件依赖规则，避免循环依赖 |

### 7.5 核心信念

> **功能模块像插件一样可插拔**，不是一句口号，而是需要：
> 1. **架构基石**：module-registry.yml + 插件契约 + SPI
> 2. **生命周期管理**：install → enable → disable → uninstall
> 3. **依赖解析**：模块依赖 + 插件依赖 + 基础设施依赖
> 4. **动态感知**：前端菜单动态加载 + 网关路由动态生效
> 5. **向后兼容**：每个插件可独立启用/禁用，不影响核心功能
>
> 通过插件化架构，mykng 可以：
> - 按需启用功能（个人用户轻量、团队用户全量）
> - 平滑扩展新功能（不影响已有功能）
> - 灵活上下线模块（禁用即停止，不破坏数据）
> - 拥抱 AI 趋势（LLM 插件可选启用）

## 附录 C：术语表

| 术语 | 含义 |
|------|------|
| 插件（Plugin） | 可独立安装/卸载/启用/禁用的功能模块 |
| 插件契约（Plugin Contract） | 插件必须包含的组件规范（后端 + 前端 + 数据库 + 配置 + 路由） |
| 插件 SPI（Service Provider Interface） | 插件服务提供者接口，用于插件发现和扩展 |
| 插件生命周期 | install → enable → disable → uninstall 四个状态 |
| module-registry.yml | 模块与插件的单一事实来源 |
| 可插拔（Pluggable） | 模块可像插件一样插入/拔出，不影响其他模块 |
| 分布式单体（Distributed Monolith） | 部署上是微服务，但开发/部署/版本高度耦合 |
| 事件驱动（Event-Driven） | 服务间通过异步事件通信 |
| RAG（Retrieval-Augmented Generation） | 检索增强生成，基于知识库的 LLM 问答 |
| CRDT（Conflict-free Replicated Data Type） | 无冲突复制数据类型，用于协作编辑 |
