# RAG 记忆增强部署方案

> 为小桉（OpenClaw Agent）添加向量检索记忆能力，解决模型长期记忆不足的问题。

## 一、方案选型

| 项目 | 选择 |
|------|------|
| **向量数据库** | Qdrant（Docker 容器化，REST API） |
| **Embedding 模型** | `bge-small-zh-v1.5`（轻量，纯中文+技术文档场景够用） |
| **部署方式** | Docker Compose，Qdrant + Embedding 服务同机部署 |
| **部署位置** | 内网 Debian（192.168.31.182）— 全部部署 |
| **数据目录** | `/mnt/shared/temp/rag-data/`（共享目录下，持久化不受 Docker 生命周期影响） |
| **龙虾主机访问** | 通过 Tailscale 网络调用内网 Debian 的 REST API |
| **自动化机制** | MCP Server 注册到 OpenClaw，agent 工具列表中自动暴露 `memory_search` 和 `memory_write` |

## 二、架构设计

### 2.1 部署拓扑

```
内网 Debian（192.168.31.182）
  ├── Qdrant 容器 (:6333 REST API / :6334 gRPC)
  └── Embedding 服务容器 (:8081 HTTP API)
        └── bge-small-zh-v1.5 (CPU 推理)
        
龙虾主机（49.51.245.134）
  └── rag-memory MCP Server（stdio 模式）
        ├── memory_search（每次消息自动检索）
        └── memory_write（主动写入）

龙虾主机通过 Tailscale（100.105.196.63）访问内网 Debian 的两个服务
```

### 2.2 数据流向

```
用户消息
  ↓ 系统层面自动暴露 memory_search 工具
小桉（OpenClaw Agent 必须调 memory_search）
  ↓ 通过 mcporter → rag-memory MCP Server
Embedding 服务（文本 → 向量）
  ↓ 检索相关记忆
Qdrant 向量库
  ↓ 返回 top-5 相关记忆片段
小桉（拼接至上下文）
  ↓
模型回答
```

### 2.3 自动化检索流程（MCP 方式）

```
用户："上次 Hive 那个问题后来怎么解决的？"

① OpenClaw 工具列表中有 rag-memory.memory_search 工具
② mcporter 路由到 rag-memory MCP Server，调用 memory_search(query="Hive")
③ MCP Server 内部：embed(query) → search(vector) → 返回结果
④ 结果格式化为文本返回给 OpenClaw
⑤ 小桉将记忆拼入上下文
⑥ 调用大模型回答
```

## 三、数据模型设计

### 3.1 Qdrant Collection 结构

**Collection 名：** `memory`

**每条 Point 的结构：**

```json
{
  "id": "<uuid>",
  "vector": [0.123, 0.456, ...],  // 512 维 float 数组
  "payload": {
    "content": "记忆片段的原文摘要（200~500 字）",
    "source": "知识时光机 | 每日日志 | 对话记录",
    "date": "2026-06-09",
    "tags": ["配置", "Hive", "MySQL", "部署"],
    "category": "备忘录 | 经验 | 知识",
    "path": "/home/liangzi/document/备忘录/Hive定时任务_20260602.md",
    "timestamp": 1749465600
  }
}
```

### 3.2 分块策略

| 参数 | 值 | 说明 |
|------|-----|------|
| chunk_size | 300 token | 中文平均 1.5 字/token，约 450 字一段 |
| 重叠 overlap | 30 token | 避免上下文截断丢失语义 |
| 单段最大长度 | 500 字 | 模型 context 里不宜过长 |

### 3.3 检索策略（阶段一）

| 参数 | 值 | 说明 |
|------|-----|------|
| limit (top-k) | 5 | 每次检索取前 5 条最相关 |
| score_threshold | 0.65 | 低于 0.65 的丢弃（不够相关就不查） |
| 检索模式 | 稠密向量（Dense） | 阶段一先只用向量相似度 |
| 排序 | cosine similarity | 余弦相似度 |

> 阶段二考虑加 BM25 稀疏检索做混合搜索，提升名词/代码关键词的命中率。

## 四、组件详情

### 4.1 Qdrant

- **镜像：** `qdrant/qdrant:latest`
- **REST API 端口：** :6333
- **gRPC 端口：** :6334
- **数据持久化：** 挂载 `/mnt/shared/temp/rag-data/qdrant/storage` 到容器的 `/qdrant/storage`
- **配置：** 使用默认配置，后续按需调优

### 4.2 Embedding 服务

- **镜像：** `rag-embedding:bge-small-zh-v1.5`（自定义构建）
- **源码位置：** `/home/root01/rag-embedding/`
- **模型：** `BAAI/bge-small-zh-v1.5`（HuggingFace，512 维，CPU 推理，~100MB）
- **API 设计：**

| 端点 | 方法 | 参数 | 返回 |
|------|------|------|------|
| `/embed` | POST | `{"text": "要编码的文本"}` | `{"vector": [0.123, ...], "dim": 512}` |
| `/embed_batch` | POST | `{"texts": ["文本1", "文本2", ...]}` | `{"vectors": [[...], [...]], "dim": 512}` |
| `/health` | GET | 无 | `{"status": "ok", "model": "bge-small-zh-v1.5"}` |

- **性能预估：** CPU 单次推理约 50ms（300 token 文本），批次 10 条约 200ms

### 4.3 MCP Server（核心组件）

**位置：** `/opt/rag-mcp/mcp_server.py`
**传输方式：** STDIO 模式（通过 stdin/stdout 读写 JSON-RPC 2.0）
**运行用户：** 由 mcporter 管理，无需 systemd

**暴露两个工具：**

| 工具名 | 功能 | 参数 | 返回 |
|--------|------|------|------|
| `memory_search` | 检索相关记忆 | `query`（必填，用户问题） | 格式化文本结果或 `NO_RELEVANT_MEMORY` |
| `memory_write` | 写入新记忆 | `content`（必填）、`source`（必填）、`tags`（可选） | 写入成功消息 |

**memory_search 内部流程（MCP Server 源码实现）：**
```
收到 parameters.query
  ↓ POST /embed（embedding 服务）
得到 512 维向量
  ↓ POST /collections/memory/points/search（Qdrant）
Qdrant 返回 top-5（含 payload 内容、score）
  ↓ 格式化输出
返回结果文本（每条含内容、来源、日期、标签、相关度）
```

**memory_write 内部流程：**
```
收到 parameters.content, source, tags
  ↓ POST /embed（embedding 服务）
得到 512 维向量
  ↓ 生成 uuid, 组装 payload
PUT /collections/memory/points（Qdrant upsert）
返回写入成功 + point id
```

## 六、自动化机制：MCP Server 注册与强制执行

### 6.1 完整注册链路

这是整套方案的核心——让 RAG 检索从"小桉自觉执行"变成系统强制执行的三个关键环节：

```
流程：内网服务 → MCP Server → mcporter → OpenClaw → 工具列表 → 小桉必须调工具
```

**环节一：内网 Debian Docker 服务**
- Qdrant（:6333）和 Embedding（:8081）运行在内网 Debian
- 通过 Tailscale（100.105.196.63）暴露给龙虾主机

**环节二：MCP Server（/opt/rag-mcp/mcp_server.py）**
- 在龙虾主机上运行，实现了 JSON-RPC 2.0 MCP 协议
- 暴露 memory_search 和 memory_write 两个工具
- 对内通过 HTTP 调用 Embedding 和 Qdrant 服务
- 对外通过 STDIO 与 mcporter 通信

**环节三：mcporter 配置注册**
- 在 `/root/.mcporter/mcporter.json` 的 `mcpServers.rag-memory` 节点配置
- 指定 command、args、env 三个字段
- mcporter 自动管理 STDI/O 子进程生命周期

**环节四：OpenClaw 配置注册（关键！）**
- 在 `/root/.openclaw/openclaw.json` 的 `mcp.servers.rag-memory` 节点配置
- 与 mcporter 配置一致（command、args、env 三个字段）
- OpenClaw 读取到此配置后，将 rag-memory 注册为 MCP Server

**环节五：工具列表自动出现（系统级强制执行）**
- 重启 OpenClaw 后，`memory_search` 和 `memory_write` 自动出现在 agent 的工具列表中
- 小桉每次收到用户消息时，工具列表中有这两个工具
- 系统层面可见 → 小桉必须调工具 → 不需要自觉翻文件

### 6.2 强制执行机制说明

```
以前（靠自觉）：
用户发消息 → 小桉需要自己"记得"去查记忆 → 容易忘

现在（系统强制）：
用户发消息 → OpenClaw 工具列表中有 memory_search → 小桉看到工具必须调 → 自动检索
```

**跟进度汇报铁律的区别：**
- RAG 的强制执行是**系统层面**的（MCP tool 注册后不可隐藏）
- 进度汇报是靠 AGENTS.md **系统注入**（prompt 层面的强制，不是 tool 层面）
- 两者本质不同：RAG 是"不得不调的工具"，进度汇报是"被迫读到的规则"

### 6.3 AGENTS.md 的 Red Lines 辅助

除了系统层面的强制，AGENTS.md 中也加了 Red Lines 保障（作为第二道防线）：

```markdown
## 🧠 RAG 记忆增强（2026-06-09 已部署）

> RAG 已通过 MCP Server 注册到 OpenClaw 工具列表，工具名为 `memory_search`（检索）和 `memory_write`（写入）。
> 回答前调用 `memory_search` 获取相关记忆。
```

同时 tools 描述中也写明了调用规则：
```
memory_search 的描述：每次用户消息都先调用此工具，有结果则拼入上下文再回答。
```

### 6.4 当前现状：MCP tool 已注册但未自动调用

> ⚠️ 2026-06-09 已知问题：memory_search 虽然已出现在工具列表中，但 OpenClaw 目前**不会在每次消息前自动调用它**。小桉需要在每次用户消息时主动调用 `rag-memory__memory_search` 工具来检索记忆。后续可以考虑：
> - 通过 gateway 的 hooks/middleware 实现自动拦截检索
> - 每次回复前先调 memory_search 的固定流程（靠 AGENTS.md 规则强化）

### 7.1 部署步骤（实际执行的）

> **注意：** 之所以选择内网 Debian 而非龙虾主机，是因为龙虾主机仅 3.6GB 内存 + 59GB 磁盘（76%已用），
> Docker 构建 PyTorch 镜像时 OOM，宿主 Python 也因内存不足反复被 kill。
> 内网 Debian 有 7.6GB 内存 + 81GB 可用磁盘，足够承载两个服务。
> Tailscale 局域网延迟仅 1-2ms，对整体检索耗时影响可忽略。

#### 1. 内网 Debian：准备数据目录

```bash
mkdir -p /mnt/shared/temp/rag-data/{qdrant/storage,models}
```

#### 2. 内网 Debian：构建 Embedding 镜像

```bash
cd ~/rag-embedding/
docker build -t rag-embedding:bge-small-zh-v1.5 .
```

> **关键坑：** 构建过程中需从 HuggingFace 下载模型（约 100MB）。内网 Debian 需通过 Clash 代理出网，Docker daemon 已配置 proxy。Embedding 容器运行时还需配置 `http_proxy=http://172.17.0.1:7890` 环境变量，否则容器内 Python 无法连接 HuggingFace。

#### 3. 内网 Debian：docker-compose.yml

```yaml
services:
  qdrant:
    image: qdrant/qdrant:latest
    container_name: rag-qdrant
    ports:
      - "6333:6333"
      - "6334:6334"
    volumes:
      - /mnt/shared/temp/rag-data/qdrant/storage:/qdrant/storage
    restart: unless-stopped

  embedding:
    build: .
    image: rag-embedding:bge-small-zh-v1.5
    container_name: rag-embedding
    ports:
      - "8081:8081"
    environment:
      - MODEL_NAME=BAAI/bge-small-zh-v1.5
      - MODEL_CACHE=/app/models
      - http_proxy=http://172.17.0.1:7890
      - https_proxy=http://172.17.0.1:7890
      - no_proxy=localhost,127.0.0.1,192.168.0.0/16,172.16.0.0/12,10.0.0.0/8,.local
    volumes:
      - /mnt/shared/temp/rag-data/models:/app/models
    restart: unless-stopped
```

## 八、场景总结：MCP Server 实现的完整服务链路

```
用户发消息
  ↓
① 工具列表中可见 rag-memory.memory_search（系统层面暴露）
  ↓
② 小桉调用 memory_search(query="用户问题")
  ↓ 通过 mcporter 路由
③ rag-memory MCP Server 收到请求
  ↓ 对内调用
④ Embedding 服务（POST /embed）→ 得到向量
  ↓
⑤ Qdrant（POST /collections/memory/points/search）→ 得到结果
  ↓
⑥ MCP Server 格式化为文本
  ↓
⑦ OpenClaw 接收工具返回结果
  ↓
⑧ 小桉将记忆拼入上下文
  ↓
⑨ 大模型回答
```

## 九、阶段二优化方向

| 方向 | 说明 | 优先级 |
|------|------|--------|
| 混合搜索 | 加入 BM25 稀疏检索，提升代码/关键词匹配 | 高 |
| 重排序（rerank） | 检索后 rerank，提升 top-k 精确率 | 高 |
| 分块策略调优 | 根据实际命中率调整 chunk_size / overlap | 中 |
| 记忆时效降权 | 旧记忆检索时降权，新记忆优先 | 中 |
| 会话级长短期记忆 | 当前会话上下文 + 向量库长期记忆结合 | 中 |
| Embedding 模型升级 | 升到 `bge-m3` 提升多语言精度 | 低 |
| 知识时光机直写 Qdrant | 知识时光机脚本拆分为增量 + 全量写入 | 低 |
| 自动调用 memory_search | OpenClaw hooks/middleware 自动拦截检索 | 低 |

## 十、注意事项

1. **Embedding 模型首次启动需下载（约 100MB）**，可预先在共享目录缓存
2. Volume 映射到共享目录，方便其他机器访问
3. 每次方案变更前，**先更新本方案文档，再动手**
