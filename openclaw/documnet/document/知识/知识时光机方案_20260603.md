## 一、核心理念

> **手动维护是源头，自动验证保准确，全量快照可回溯**

知识时光机不是替代手动维护，而是在手动维护的基础上做验证和优化：

```
每天 02:00 知识时光机跑完
    ↓
1. 原文快照 → 把 document 目录完整复制到快照中
2. 增量采集 → 记录今天变了什么
3. 全量聚合 → 根据最新状态生成 9 个知识文件
4. 动态验证 → 从刚产出的全量文件解析验证清单，实时生成临时验证脚本跑一遍
5. 覆盖 document → 原文快照写回 + 全量输出覆盖对应位置
    ↓
document 目录保持最新：手动改的保留，自动生的更新
```

### 覆盖规则

**核心逻辑：** 原文快照原封不动全部写回 document，全量输出（9 个文件）额外覆盖掉对应位置的老版本。

```
覆盖 document 时：
  1. cp -r 原文快照/* → document/    ← 所有手动维护的内容保持不变
  2. cp 全量部分/XX.md → document/对应位置  ← 9个文件覆盖旧版
```

这样 document 目录里不管有什么，原文快照全保留，只有那 9 个知识时光机能生成的文件被换成已验证的最新版。

## 六、动态验证机制（核心）

### 为什么要动态生成验证脚本？

**传统做法（已废弃）：** 在知识时光机脚本里硬编码 SSH 验证逻辑，写死机器 IP、密码、端口。

```
❌ 问题：今天新加了一台机器/改了端口/换了密码，就得改脚本
❌ 问题：验证逻辑和全量生成逻辑高度耦合，改一处影响全局
```

**当前做法（动态生成）：**

```
全量部分/                  → 知识时光机根据最新状态生成
├── 07-账密汇总.md         → 解析出所有主机 + 账密
├── 05-端口速查表.md       → 解析出所有端口映射
├── 08-域名映射.md         → 解析出所有域名 + SSL
├── 04-应用依赖关系.md     → 解析出所有依赖链路
├── 06-运维命令速查.md     → 解析出 SSH 命令模板
        ↓
动态验证生成器（verify_generator.sh）
        ↓
临时验证脚本（verify_YYYY-MM-DD.sh）→ 执行验证 → 输出验证结果
```

**这样有什么好处？**

| 场景 | 以前 | 现在 |
|------|------|------|
| 新增一台机器 | 改脚本，把新机器IP写进去 | 只需更新 07-账密汇总.md，验证自动包含新机器 |
| 改了某个端口 | 改脚本里的端口号 | 只需更新 05-端口速查表.md，验证自动对新端口 |
| 域名换了 | 改脚本 | 只需更新 08-域名映射.md，验证自动对 |
| 应用依赖变了 | 改脚本 | 只需更新 04-应用依赖关系.md，验证自动跟进 |

### 解析规则

| 全量文件 | 解析方式 | 提取内容 | 验证方式 |
|---------|---------|---------|---------|
| 07-账密汇总.md | awk 解析表格 `\|` 分隔 | [机器名, IP, 用户, 密码, 用途] | sshpass SSH |
| 07-账密汇总.md | awk 解析"应用服务"表格 | [应用名, URL, 账号, 密码] | curl 状态码 |
| 05-端口速查表.md | awk 解析表格 | [端口, 机器, 服务, 对外方式] | nc -zv |
| 08-域名映射.md | awk 解析表格 | [域名, IP, SSL状态] | dig + curl |
| 04-应用依赖关系.md | grep + awk | [依赖链路] | 按链路逐跳验证 |
| 06-运维命令速查.md | grep SSH 命令块 | [SSH模板] | 辅助生成验证参数 |

### 验证执行

```
临时验证脚本路径: /tmp/knowledge-time-machine/verify_YYYY-MM-DD.sh
验证结果输出:     /tmp/knowledge-time-machine/verify_YYYY-MM-DD.log
验证报告追加至:   知识时光机/YYYY-MM-DD/增量部分/矛盾提醒.md
```

### 安全注意事项

- 临时验证脚本中**不能明文写入密码**（账密汇总里有密码，但生成临时脚本时只写 SSH 命令模板，密码通过环境变量传入）
- 临时验证脚本运行后自动删除
- 验证结果中不暴露密码原文
