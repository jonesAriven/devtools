# 统一登录认证设计方案

## 一、现状分析

### 现有系统

| 系统 | 技术栈 | 登录方式 | 部署路径 |
|------|--------|----------|----------|
| kb-auth (认证服务) | Spring Boot 3.4 + Java 21 | JWT (HS512) | kb-gateway:8090/kb/api/auth |
| Portal 看板 | Vue3 + Spring Boot | 接入 kb-auth | /portal/ |
| kb-ops 运维 | Vue3 + Spring Boot | 接入 kb-auth | /ops/ |
| mykng 知识库 | Vue3 + Spring Cloud | kb-auth + 网关 | /kb/ |

### 当前问题

1. **登录体系分散**：Portal、kb-ops、知识库各有各的登录页面，用户需要分别登录
2. **鉴权方式不统一**：
   - 知识库：通过 kb-gateway 统一鉴权，网关验证 JWT 后注入 `X-User-Id`
   - kb-ops：原设计依赖网关，但实际部署绕过了网关，导致 403
   - Portal：直接调用 kb-auth 验证，自己管理 token
3. **新系统接入成本高**：每个新系统都要重复实现登录页、token 管理、拦截器等

## 二、设计目标

1. **统一账号体系**：所有系统共用一套用户账号（kb-auth）
2. **单点登录 (SSO)**：一次登录，所有系统自动获得访问权限
3. **统一鉴权**：后端服务验证 JWT 的方式标准化
4. **快速接入**：新系统接入只需少量配置和代码
5. **安全可靠**：支持 token 刷新、黑名单、过期处理

## 四、核心设计

### 4.1 认证方式：JWT + 双 Token

**为什么是 JWT？**
- 无状态，服务端不需要存储 session
- 跨语言、跨系统通用性强
- 可以携带用户基本信息，减少数据库查询

**双 Token 机制：**
- **Access Token**：访问令牌，有效期短（默认 2 小时）
- **Refresh Token**：刷新令牌，有效期长（默认 7 天）
- Access Token 过期后，用 Refresh Token 换取新的 Access Token

**JWT Payload 结构：**
```json
{
  "sub": "1",           // 用户ID
  "username": "admin",  // 用户名
  "type": "access",     // token类型: access / refresh
  "iat": 1719999999,    // 签发时间
  "exp": 1720007199     // 过期时间
}
```

**JWT 签名算法：** HS512 (HMAC-SHA512)
- 对称加密，密钥共享
- 性能高，适合内部系统
- 密钥长度至少 64 字节（256 bits 以上）

### 4.2 后端服务鉴权方案：两种模式

#### 模式 A：独立鉴权（推荐用于独立部署的服务）

**适用场景**：Portal、kb-ops 等独立部署、不经过网关的服务

**实现方式**：
- 每个后端服务自己验证 JWT
- 共享 JWT 密钥（与 kb-auth 一致）
- 实现 JwtAuthenticationFilter
- 从 Authorization: Bearer <token> 中提取并验证

**接入步骤**：
1. 引入 jjwt 依赖
2. 添加 `jwt.secret` 配置（与 kb-auth 保持一致）
3. 复制 `JwtTokenProvider` 和 `JwtAuthenticationFilter`
4. 在 SecurityConfig 中注册过滤器

**代码示例**：
```java
// JwtTokenProvider.java - 工具类，验证和解析 JWT
@Component
public class JwtTokenProvider {
    private final SecretKey key;
    
    public JwtTokenProvider(@Value("${jwt.secret}") String secret) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }
    
    public boolean validateToken(String token) { ... }
    public Long getUserIdFromToken(String token) { ... }
    public String getUsernameFromToken(String token) { ... }
    public String getTokenType(String token) { ... }
}
```

```java
// JwtAuthenticationFilter.java - 过滤器
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider jwtTokenProvider;
    
    @Override
    protected void doFilterInternal(...) {
        String token = resolveToken(request); // 从 Authorization header 提取
        if (StringUtils.hasText(token) && jwtTokenProvider.validateToken(token)) {
            Long userId = jwtTokenProvider.getUserIdFromToken(token);
            // 构建 Authentication 并存入 SecurityContext
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }
        filterChain.doFilter(request, response);
    }
}
```

#### 模式 B：网关鉴权（推荐用于微服务集群）

**适用场景**：知识库的微服务（kb-knowledge、kb-file 等）

**实现方式**：
- 请求先经过 kb-gateway
- 网关统一验证 JWT
- 验证通过后，将用户 ID 注入请求头 `X-User-Id`
- 后端服务信任网关，直接从 `X-User-Id` 获取用户信息

**优缺点对比**：

| 维度 | 独立鉴权 (模式 A) | 网关鉴权 (模式 B) |
|------|-------------------|-------------------|
| 部署灵活性 | 高，可独立部署 | 低，依赖网关 |
| 性能 | 每个服务都要验证 JWT | 只需验证一次 |
| 一致性 | 需确保各服务密钥一致 | 网关统一管理 |
| 适用场景 | 独立服务、异构系统 | 微服务集群 |

**建议**：
- 独立系统（Portal、kb-ops 等）使用 **模式 A（独立鉴权）**
- 知识库微服务集群继续使用 **模式 B（网关鉴权）**
- 两种模式并存，各取所长

### 4.3 前端接入方案

#### 统一前端 SDK（可选，后续建设）

提供一个 npm 包 `@kb/auth`，封装：
- 登录/登出方法
- Token 存储和管理
- Token 自动刷新
- Axios 请求拦截器
- 路由守卫

#### 当前接入方式（各系统自行实现）

每个系统前端需要实现：

1. **登录页面**：用户名密码登录，调用 kb-auth 的 `/login` 接口
2. **Token 存储**：accessToken + refreshToken 存入 localStorage
3. **请求拦截器**：
   - 请求时自动携带 `Authorization: Bearer <token>`
   - 401 时自动用 refreshToken 刷新
   - 刷新失败则跳转到登录页
4. **路由守卫**：检查 token，未登录跳转登录页

#### API 路径约定

为了 Nginx 代理方便，约定：
- 认证 API 路径：`/xxx/auth-api/` → 代理到 kb-auth
- 业务 API 路径：`/xxx-api/` → 代理到对应后端

例如：
- Portal: `/portal/auth-api/` → kb-auth, `/portal/api/` → portal-server
- kb-ops: `/ops/auth-api/` → kb-auth, `/ops-api/` → kb-ops

### 4.4 Nginx 代理配置模板

```nginx
# ====== 新系统 X 模板 ======

# 1. 认证 API（代理到 kb-auth）
location /xxx/auth-api/ {
    proxy_pass http://kb-auth-server/kb/api/auth/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 2. 业务 API（代理到对应后端）
location /xxx-api/ {
    proxy_pass http://xxx-backend/xxx/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 3. 前端静态资源
location /xxx/ {
    alias /var/www/xxx-web/;
    index index.html;
    try_files $uri $uri/ /xxx/index.html;
    access_log off;
}
```

## 五、新系统接入流程

### 后端接入（5 步）

1. **添加依赖**
   ```xml
   <dependency>
       <groupId>io.jsonwebtoken</groupId>
       <artifactId>jjwt-api</artifactId>
       <version>0.12.5</version>
   </dependency>
   <dependency>
       <groupId>io.jsonwebtoken</groupId>
       <artifactId>jjwt-impl</artifactId>
       <version>0.12.5</version>
       <scope>runtime</scope>
   </dependency>
   <dependency>
       <groupId>io.jsonwebtoken</groupId>
       <artifactId>jjwt-jackson</artifactId>
       <version>0.12.5</version>
       <scope>runtime</scope>
   </dependency>
   ```

2. **添加配置**
   ```yaml
   jwt:
     secret: ${JWT_SECRET:YourSuperSecretKeyForJwtTokenGenerationMustBeAtLeast256BitsLong!!}
   ```

3. **复制 3 个文件**
   - `JwtTokenProvider.java` - JWT 工具类
   - `JwtAuthenticationFilter.java` - 认证过滤器
   - `SecurityConfig.java` - Security 配置（按需修改白名单）

4. **配置 Nginx 代理**
   - 添加 auth-api 代理到 kb-auth
   - 添加业务 API 代理

5. **测试验证**
   - 登录获取 token
   - 携带 token 访问业务 API
   - 验证 401/403 处理

### 前端接入（5 步）

1. **创建登录页面**：用户名密码表单
2. **实现 API 封装**：
   ```typescript
   // auth.ts
   export function login(data: { username: string; password: string }) {
     return authRequest.post('/login', data)
   }
   export function refreshToken(refreshToken: string) {
     return authRequest.post('/refresh', { refreshToken })
   }
   ```
3. **配置请求拦截器**：
   - 请求时携带 Authorization header
   - 响应 401 时自动刷新 token
4. **配置路由守卫**：未登录跳转登录页
5. **部署配置**：Nginx 添加静态资源和 API 代理

## 六、安全设计

### 6.1 Token 安全

| 措施 | 说明 |
|------|------|
| 短有效期 | Access Token 2 小时，降低泄露风险 |
| 刷新机制 | Refresh Token 7 天，无感刷新 |
| 黑名单 | 登出时 token 加入黑名单，立即失效 |
| HTTPS | 生产环境必须 HTTPS，防止窃听 |
| HttpOnly | （可选）Refresh Token 存 HttpOnly Cookie，防 XSS |

### 6.2 常见攻击防护

- **XSS**：前端做好输入输出转义，token 存 localStorage 注意 XSS 风险
- **CSRF**：使用 JWT + Authorization header 天然防 CSRF
- **暴力破解**：登录接口加验证码或限流
- **中间人攻击**：强制 HTTPS

## 七、与 Portal 看板的集成

Portal 作为所有系统的入口，承担以下角色：

1. **统一入口**：用户从 Portal 登录，然后跳转到各个子系统
2. **Token 传递**：
   - 方案一（当前）：各子系统独立登录，体验稍差但简单
   - 方案二（未来优化）：Portal 登录后，通过 URL 参数传递 token，子系统自动登录
3. **系统管理**：Portal 管理所有系统的元数据（名称、图标、URL、分类等）

## 十、总结

**核心原则**：
1. **kb-auth 是唯一认证中心**：所有系统共用一套账号和 JWT 密钥
2. **后端鉴权两种模式并存**：独立服务自己验签，微服务走网关
3. **前端各系统独立实现**：后续统一封装 SDK 降低成本
4. **Nginx 代理标准化**：auth-api + 业务 API + 静态资源三段式

**新系统接入成本**：
- 后端：约 0.5 人天（复制粘贴 + 配置）
- 前端：约 1 人天（登录页 + 拦截器 + 路由守卫）

这个设计兼顾了灵活性和一致性，既能快速接入新系统，又能保证安全可靠。
