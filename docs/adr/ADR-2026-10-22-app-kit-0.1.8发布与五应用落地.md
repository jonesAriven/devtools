## 1. 背景与问题

- `T-ENG-18`（坑 #44）在 R13 已完成组件侧修复（0.1.8：权限探针失败输出可归因告警），但**未发 Nexus**，五应用锁文件仍钉 0.1.7 ⇒ 修复**生产未生效**。
- 0.1.8 的核心承诺必须落在生产才算闭环：kb-ops（`T-ENG-17` 现场，权限链双通道断裂、长期静默 fail-open）应出现归因告警；其余四应用成功路径应**零告警、零额外请求**。
- 验证过程中反向**抓出回归库自身的两个缺陷**（详见 §4），不修则任何 console 类结论都不可信。

## 2. 决策与范围

| 项 | 决策 | 理由 |
|---|---|---|
| 发布通道 | 走既有 Woodpecker（repo 5 push 自动发包） | 四段验（仓库→Nexus→锁文件→线上产物）的既有机制，不另造 |
| 锁文件改法 | 只改目标依赖条目（importers version + snapshots/packages 键），**specifier 与 package.json 零改动** | `--frozen-lockfile`/`npm ci` 校验的是 specifier 一致性而非 version；改 specifier 属无谓漂移 |
| cosmic（npm 项目） | 二进制安全补丁（原文件 CRLF），禁文本读写归一化 | 文本读写会产生整文件 2377 行 diff |
| 流水线触发 | devtools 四前端**一次只跑一条**（顺序 kb-ops-web→kb-web→infra-monitor-web→portal-web） | `.woodpecker.yml` 的 `sync-ci-scripts` 会清空重写 `/mnt/shared/woodScript`，并发必 races |
| Gitee 推送被网络阻断时 | 从 mykng 克隆 `git fetch github main && git push origin FETCH_HEAD:main` 代推 | 本机直推偶发阻断的既定绕行 |

## 4. 回归库两个真缺陷（本轮最大方法论产出，均已实修 + 固化）

| # | 缺陷 | 实证 | 修法 |
|---|---|---|---|
| 坑 #46 | headless chromium 的 CDP **不上报页面 console API**（`Log.entryAdded` 只收浏览器原生网络错误）⇒ console 断言系统性漏抓 | J6 对照实验：页面内手动 `console.warn/error` 均无事件上报；J2/J3/J4 三轮「kb-ops 零告警」全为假阴性 | `r14_lib.P` 新增 `wrap_console()`/`warn_log()`，`appkit()` 改 CDP + 页面内 `__WARN_LOG__` 双源合并；K 轮回归 PASS |
| 坑 #45 | ElMessage toast 默认 3s 过期 vs 断言在提交后 6-8s 取全文 ⇒ 「错密无错误提示」6 条全误判 | H 探针 300ms 轮询实证三应用 toast 均正常弹出 | C 脚本改提交后实时轮询 5s（toast + inline 双选择器）拼入断言全文；复跑 + R14-I targeted（40 PASS/0 FAIL）全绿 |

**判据（防复发）**：console 类断言一律先页面内包装；「代码+产物+网络」三边证据都指向某行为应发生而 console 说没有时，**先怀疑抓取链、再怀疑产品**。

## 5. 0.1.8 生产效果验证（三层证据，J 系列）

1. **产物层**：双签名串（`权限探针失败`+`fail-open`）+ 诊断链常量（`http-not-200`/`network-error`）均在 bundle。
2. **网络层**：登录后导航**带 `meta.perm` 的业务路由**（`/ops/hosts` 等）——失败路径 = 同 URL 两次带票请求（fetchPermissions + diagnose），成功路径 = 一次。
3. **console 层**（页面内包装）：**kb-ops 出现可归因告警**（`权限探针失败：GET /ops-api/auth/permissions?client=marschat-kbops · HTTP 404 · 后果：fail-open…`）⇒ `T-ENG-17` 现场自证；infra-SSO / kb-web / portal / cosmic **零告警、零额外请求**。

⚠️ 两个时序要点（J2 盲区，各浪费一轮）：① `createAuthGuard` 对无 `meta.perm` 的路由直接放行，`ensurePermissions` 不跑 ⇒ 只着陆 dashboard 验证告警必然空手而归；② 登录前 bootstrap 探针无票是**预期行为**（0.1.8 有意不诊断），判据看「有票之后的探针」。

## 6. 回归结论与遗留

- 合计：SSO 187/37（35 条瞬态级联 + 2 条已知）· 账密 164/6（全映射已知项）· 负例 toast 修复后 146+40 PASS/0 真失败 · SLO+应用台 28/0 · 服务端 12 容器日志 **0 真实故障**（四类归因：负例自伤 / 外部会话部署 / Spring Security DEBUG 被 grep 误匹配 / nexus 定时 WARN 噪声）。
- **环境碰撞澄清**：测试窗口与外部会话部署重叠（#860 Nacos、kb-gateway 栈重建、cosmic #126/#127），碰撞项全部 targeted 补跑，**无一条归因产品缺陷**。
- **顺带修正两条既有记录**：`T-ENG-20` 的「infra 账密权限探针 401」**证伪**（实为登录前无票探针；带票 200），真症状 = 全页面加载后 bootstrap 无票 + 被踢 `/infra/login?slo=1`；`T-ENG-17` 的「跨域恒 403」本轮观测为 **200**（两轮并列记录，待下轮带非超管票据定性）。
- **遗留（均需良哥拍板，不在本轮范围）**：kb-ops 权限链根因修复（`T-ENG-17`：后端补同源代理 + 前端 `permOptions.issuer` 改同源）；infra 账密会话令牌键取证（`T-ENG-20`）。
