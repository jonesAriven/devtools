# ADR-2026-09-08 · 统一认证单点登录（auth-center + OIDC）

- **状态**：部分实施（核心链路已上线，2 个应用待接入）
- **归属**：cross-project
- **关联**：
  - `devtools/docs/统一登录认证设计方案.md`（2026-07-04，前序方案，kb-auth 时代）
  - hermes 技能 `devops/sso-integration-planning/references/mykng-sso-audit-20260821.md`
  - 走查报告 `WorkBuddy/2026-09-07-22-00-13/全应用浏览器走查报告.md`（2026-09-07 真浏览器实证）

## 背景

- **起因**：6 个自研应用（portal / kb-web / kb-ops / infra-monitor / activecode / tokenhub）各有独立登录页与独立 token 管理，用户进一个系统登一次，账号体系事实上分裂。
- **历史约束**：
  - 2026-07-04 方案确立「kb-auth 为唯一认证中心，JWT(HS512) + 双 token，后端鉴权分独立验签(A)与网关鉴权(B)两模式」，但**未实现真正单点**——方案七章写明「各子系统独立登录，体验稍差但简单」，SSO 被列为中期优化。
  - 2026-08-21 审计实测暴露：kb-auth / kb-gateway **不在 mykng 本机**；Portal 另起一套 hutool JWT（密钥 `PortalJwtSecretKey2026!`），形成**第二个认证域**，与 kb-auth 密钥不同、登录态不互通。
- **触发事件**：2026-09 需要把全部自研应用纳入统一入口（Portal 面板）单点进入，私有 JWT 拼装方案每接一个应用都要复制登录页 + 拦截器 + token 管理，成本不可接受。

## 考虑过的方案

- **A：沿用 kb-auth 自研 JWT + 各系统独立登录**
  - 优点：零改动，现状即可用
  - 缺点：不是 SSO；新系统接入约 1.5 人天（后端 0.5 + 前端 1）；密钥靠人工在多服务间同步，已发生过密钥不一致导致 403

- **B：以 Portal 为 SSO 中心，各系统共享 Portal JWT 密钥**
  - 优点：Portal 在 mykng 本机、可控；改造最小（hermes 方案 P1 已对 infra-monitor 落地：1 配置 + 3 行代码）
  - 缺点：仍是**私有协议**；Portal 从"入口看板"变成"认证基础设施"，职责耦合；Grafana / MinIO / Nacos / Uptime Kuma 等第三方系统无法接私有 JWT，只能等 Portal 自研 OIDC Provider（P3 约 100 行）补上

- **C：独立部署标准 OIDC 授权服务器（Spring Authorization Server）作为唯一认证域**
  - 优点：协议标准化，自研与第三方一律走 OIDC；客户端注册落库，新增应用插一条记录即可，不改代码；技术栈与现有 Spring Boot 3.4 / Java 21 / MySQL 一致，运维成本 = 一个 jar
  - 缺点：多一个服务要运维；成为新的单点故障（SPOF）；老 kb-auth 体系需共存过渡

- **D：引入 Keycloak / Casdoor 等成熟 IAM**
  - 优点：开箱即用的用户联邦、MFA、SAML、审计
  - 缺点：**过重**——额外一套内存与运维体系、独立数据库与升级链路；当前资产规模（个位数应用、几十账号）收益不抵成本

## 决策

**选 C**：独立部署 `auth-center`（Spring Authorization Server），issuer = `https://auth.marschat.online`，各应用作为标准 OIDC Client 接入。

同时保留 B 的既有改造成果（infra-monitor / activecode 已按共享密钥方式改过）作为过渡，并让 auth-center **沿用与 kb-auth 相同的 JWT 密钥**，使旧体系签发的 token 在过渡期内仍可被验签，避免一次性切换造成全站掉线。

## 理由

1. **协议 > 私有实现**：B 的致命伤是每个第三方系统都要等 Portal 自研适配；C 用标准 OIDC 后，Grafana / MinIO / Nacos / Kuma 只需在各自配置里填 issuer 与 client-id，零代码。
2. **接入成本从"人天"降到"一条记录"**：`RegisteredClientRepository` 走 JDBC，客户端信息存 `kb_auth` 库，新应用接入不再需要复制 `JwtTokenProvider` / `JwtAuthenticationFilter` / `SecurityConfig` 三件套。
3. **成本可控**：不引入新语言、新中间件类型，复用现有 MySQL 与容器部署流水线（Woodpecker + drone-ssh），符合"所有服务必须容器化"的既有铁律。
4. **D 被否**：过度工程。等应用数或合规要求（等保/MFA/SAML）真正上来时再评估，本 ADR 已记录该演进路径。

## 后果

**好处**

- 一次登录，portal / kb-web / activecode / infra-monitor 免登互跳（已实测）
- 新应用接入从 ~1.5 人天降为「插一条 registered_client 记录 + 前端加一个按钮」
- 第三方系统（Grafana / MinIO / Nacos / Kuma）具备标准 OIDC 接入条件
- 账号管理收敛到一处（AdminUserController + Portal 用户管理页）

**代价**

- auth-center 成为**单点故障**：它挂了，所有接入应用的 SSO 通道同时失效
- 多一个容器要监控、备份（`kb_auth` 库）、升级
- 老 kb-auth 体系仍需共存一段时间，两套认证逻辑并存增加认知负担

**已知风险与监控点**

1. ⚠️ **SPOF**：需纳入健康检查与告警（容器 exit、`auth.marschat.online` HTTP 码、8085 端口可达性）
2. ⚠️ **issuer 一致性**：issuer 与客户端实际访问域名不一致会直接导致 token 校验失败；换域名/换入口必须同步改 `AUTH_ISSUER`
3. ⚠️ **密钥共享面扩大**：`jwt.secret` 已是明文配置且跨多服务共享，泄露影响面覆盖全部接入应用 —— 后续应评估轮换机制或非对称密钥（RS256）
4. ⚠️ **JWT 无状态的老问题仍在**：登出/黑名单未随 OIDC 一并解决，access token 15 分钟内无法主动失效
5. 📌 **欠账**：kb-ops、tokenhub 未接入 SSO；tokenhub 管理员凭据未知导致走查阻塞

**回滚方式**

- 各应用登录页**保留独立登录（用户名/密码）入口**，auth-center 不可用时用户仍可本地登录 —— 走查已实测 6 个应用独立登录路径均可用
- 服务级回滚：`docker stop auth-center` 后各应用回落到本地登录，无数据破坏性
- 协议级回滚：删除对应 `registered_client` 记录即摘除该应用的 SSO 通道，无需改代码
