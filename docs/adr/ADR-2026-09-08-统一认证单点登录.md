## 背景

- **起因**：6 个自研应用（portal / kb-web / kb-ops / infra-monitor / activecode / cosmic-studio）各有独立登录页与独立 token 管理，用户进一个系统登一次，账号体系事实上分裂。
- **历史约束**：
  - 2026-07-04 方案确立「kb-auth 为唯一认证中心，JWT(HS512) + 双 token，后端鉴权分独立验签(A)与网关鉴权(B)两模式」，但**未实现真正单点**——方案七章写明「各子系统独立登录，体验稍差但简单」，SSO 被列为中期优化。
  - 2026-08-21 审计实测暴露：kb-auth / kb-gateway **不在 mykng 本机**；Portal 另起一套 hutool JWT（密钥 `PortalJwtSecretKey2026!`），形成**第二个认证域**，与 kb-auth 密钥不同、登录态不互通。
  - **触发事件**：2026-09 需要把全部自研应用纳入统一入口（Portal 面板）单点进入，私有 JWT 拼装方案每接一个应用都要复制登录页 + 拦截器 + token 管理，成本不可接受。

## 考虑过的方案

- **A：沿用 kb-auth 自研 JWT + 各系统独立登录**
  - 优点：零改动，现状即可用
  - 缺点：不是 SSO；新系统接入约 1.5 人天（后端 0.5 + 前端 1）；密钥靠人工在多服务间同步，已发生过密钥不一致导致 403

- **B：以 Portal 为 SSO 中心，各系统共享 Portal JWT 密钥**
  - 优点：Portal 在 mykng 本机、可控；改造最小（hermes 方案 P1 已对 infra-monitor 落地：1 配置 + 3 行代码）
  - 缺点：仍是**私有协议**；Portal 从"入口看板"变成"认证基础设施"，职责耦合；Grafana / MinIO / Nacos / Uptime Kuma 等第三方系统无法接私有 JWT，只能等 Portal 自研 OIDC Provider（P3 约 100 行）补上

- **C：独立部署标准 OIDC 授权服务器（Spring Authorization Server）作为唯一认证域**
  - 优点：协议标准化，自研与第三方一律走 OIDC；客户端注册落库，新增应用插一条记录即可，不改代码；技术栈与现有 Spring Boot 3.4 / Java 21 / MySQL 一致，运维成本 = 一个 jar
  - 缺点：多一个服务要运维；成为新的单点故障（SPOF）；老 kb-auth 体系需共存过渡

- **D：引入 Keycloak / Casdoor 等成熟 IAM**
  - 优点：开箱即用的用户联邦、MFA、SAML、审计
  - 缺点：**过重**——额外一套内存与运维体系、独立数据库与升级链路；当前资产规模（个位数应用、几十账号）收益不抵成本

- **E：Cookie Domain 共享方案（本次实施）**
  - 优点：真正的"一次登录，处处可用"；无需每个应用单独配置 OIDC Client；用户体验最佳
  - 缺点：依赖同域名部署（`.marschat.online`）；Cookie 安全性需注意

## 决策

**选 C + E 组合方案**：

1. **主方案 C**：独立部署 `auth-center`（Spring Authorization Server），issuer = `https://auth.marschat.online`，各应用作为标准 OIDC Client 接入
2. **增强方案 E**：通过 Cookie Domain 共享（`.marschat.online`）实现真正的跨应用 SSO 免登
3. **组件化**：通过 `marschat-components` monorepo 统一管理前端认证组件（`LoginPanel` + `frontend-common` + `auth-components`）

同时保留 B 的既有改造成果作为过渡。

## 理由

1. **协议 > 私有实现**：B 的致命伤是每个第三方系统都要等 Portal 自研适配；C 用标准 OIDC 后，Grafana / MinIO / Nacos / Kuma 只需在各自配置里填 issuer 与 client-id，零代码
2. **接入成本从"人天"降到"一条记录"**：`RegisteredClientRepository` 走 JDBC，客户端信息存 `kb_auth` 库，新应用接入不再需要复制 `JwtTokenProvider` / `JwtAuthenticationFilter` / `SecurityConfig` 三件套
3. **真正 SSO 体验**：Cookie Domain 共享让用户在 auth-center 登录后，访问任何子域名应用都无需再次输入密码
4. **组件化复用**：`LoginPanel` 组件统一了登录 UI、SSO 按钮、忘记密码流程，新应用只需引入组件并配置即可
5. **成本可控**：不引入新语言、新中间件类型，复用现有 MySQL 与容器部署流水线

### 功能特性

#### LoginPanel 组件功能

1. **独立登录**：用户名/密码表单，支持自定义登录 API
2. **SSO 登录**：OIDC authorization_code + PKCE 流程
3. **忘记密码**：4 步集成流程
   - 步骤 1：输入邮箱
   - 步骤 2：验证码校验
   - 步骤 3：重置密码
   - 步骤 4：成功提示
4. **可配置项**：
   - 标题、副标题、图标、颜色
   - SSO 配置（issuer、clientId、redirectUri、scope）
   - 自定义文案（按钮文字、链接文字等）

#### SSO Cookie 域共享方案

| 配置项 | 值 | 说明 |
|---|---|---|
| Cookie Domain | `.marschat.online` | 覆盖所有子域名 |
| Access Token Cookie 名 | `sso_access_token` | 与后端一致 |
| Refresh Token Cookie 名 | `sso_refresh_token` | 与后端一致 |
| 过期时间 | 2 小时（7200秒） | 可配置 |
| SameSite | `Lax` | 平衡安全与兼容性 |

#### 后端 Cookie 设置（auth-center）

- `SsoCookieProperties.java`：Cookie 配置属性类
- `SsoCookieUtil.java`：Cookie 设置/清除工具方法
- `AuthController.java`：登录/登出/刷新时自动设置 Cookie

## 好处

1. **真正 SSO**：一次登录，6 个应用免密互跳
2. **统一体验**：所有应用使用相同的登录 UI 和交互流程
3. **忘记密码**：4 步流程直接集成到登录页，无需跳转外部页面
4. **快速接入**：新应用只需：
   - 引入 `LoginPanel` 组件
   - 配置 vite 别名指向 `marschat-components`
   - 配置应用特定的标题/颜色/SSO 参数
5. **类型安全**：完整的 TypeScript 类型定义

## 代价与风险

1. **SPOF**：auth-center 挂了影响全部 SSO
2. **域名限制**：Cookie 方案要求所有应用在 `.marschat.online` 子域名下
3. **Cookie 安全**：前端 JS 无法设置 HttpOnly Cookie，需依赖后端设置
4. **过渡期**：旧 token 机制需共存一段时间

## 回滚方式

1. **应用级**：删除 `LoginPanel` 组件，恢复原登录页
2. **服务级**：停止 auth-center，各应用自动回退到本地登录
3. **协议级**：删除 `registered_client` 记录，移除 SSO 通道
