## 5. ⚠️ 本会话执行事故记录（新会话必读）

**现象**：`git rm -r` 在本机（Git Bash / Windows）出现两次失控：
- 第 1 次：`git rm -r -q <4 个目录>` 被 SIGTERM 终止 → 半完成态（工作区文件被大量删除但索引未更新）+ `.git/index.lock`（0 字节）残留
- 第 2 次：对 `infra-monitor/infra-monitor-server/src/main/java/com/kb/common` 执行 `git rm -r -q`，删的却是**整个 infra-monitor-server 树**（35 文件，含 pom.xml/Dockerfile/com/kb/infra/**）

**两次均完整恢复**，恢复方法实证有效：
```bash
cd /d/huliang/java/ideaworkspace/devtools
rm -f .git/index.lock          # 确认无活跃 git 进程（tasklist | grep git）后清锁
git reset -q && git checkout -- .
git status --short | grep -v "^??"   # 应输出 0
```

**新会话执行纪律（必须遵守）**：
1. **禁用 `git rm -r`**。删除一律用 `rm -rf <精确路径>` + `git add -u <路径>` 组合
2. **小步执行**：每次一个目录，每步后 `git status --short` 核对暂存数符合预期再进下一步
3. 若遇 `index.lock`：先 `tasklist | grep git` 确认无活跃进程，再清锁
4. 删完立即 `git status` 全量核对，任何超出预期的变更立即 `git checkout -- <路径>` 回滚

### 12.7 执行纪律事故（复用价值）

本次执行中发现并规避了一条工具级坑：**对同一文件并行发起多个 Edit 会互相覆盖**（每个 Edit 各自读取同一基线再写回，last-writer-wins）。
现象：10 个对 `module-registry.yml` 的并行 Edit 中只有 3 个生效，但**每个都返回 "Successfully edited"**，不报错。
对策：同文件改动一律**串行**，或改用一次性原子脚本（本次残余清理即改为带 dry-run 的 Python 脚本，一次完成 60+ 文件）。
§5 记录的「禁用 `git rm -r`」纪律本次遵守：删除一律 `rm -rf <精确路径>` + `git add -u`，每步核对暂存数（9 → 5 → 5 → 85 → 累计 104）全部符合预期。
