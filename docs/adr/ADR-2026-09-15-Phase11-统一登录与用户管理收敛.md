## 1. 背景：Phase 10 声称"初衷达成"，全量复核发现三处不成立

## 2. 决策

### D-1：账密的唯一真源在认证中心，应用不得自建密码体系

**规则**：自研应用可以保留**自己的登录页与独立登录体验**（不强制跳 SSO），但**密码校验必须转发认证中心** `/auth/login`（内网，公网不暴露）。

```
应用登录表单（账密）
   └─▶ 应用后端 BFF ──POST /auth/login──▶ auth-center（唯一校验方）
          ◀── {code, data.user{id,username,role,status,appRoles}}
   └─▶ 应用收敛本地影子（按 username 查/自动建档，不存密码）
   └─▶ 签发应用自身会话（JWT / Session）
```

- **保持 fail-closed**：中心不可达 → 503「认证中心不可达」，**不回退本地密码校验**（回退等于给分裂留后门）。
- 本地用户表降级为**影子**：只承载应用内业务关联（如 chat_logs.user_id），不再承载密码，不再决定身份。
- 收敛链统一为：**中心验证通过 → 按中心 username 找本地影子 → 无则自动建档 → 都不行才 403**。删除「本地同名优先」「未匹配即回退任意本地管理员」这类越权默认值。

**为什么不是反过来（各应用保留本地密码、中心只做映射）**：那样密码必然不同步（中心改密码应用不生效）、用户必然分裂（本地有、中心无），与「统一登录、用户统一管理」直接冲突。

### D-2：双用户管理菜单（回答"两个菜单是不是应该不同"）

**结论：是两个不同的东西，且必须同时存在。** 一个管「身份」，一个管「成员」。

| 维度 | A. 中心 · 平台管理台 | B. 各应用 · 本系统用户 |
|---|---|---|
| 位置 | portal `/portal/admin`（统一认证中心） | 每个自研应用各自的 `/users`（或 `/admin`） |
| 作用域 | `scope=platform` | `scope=app`（带 clientId） |
| 回答的问题 | 「平台上有**哪些人**」 | 「**谁在我这个系统里**、能干什么」 |
| 生命周期 | ✅ 创建/启用停用/重置密码/删除（墓碑） | ❌ 不删除身份，只有「移出本系统」 |
| 身份字段 | ✅ 可编辑（用户名/邮箱/昵称/全局角色） | 只读展示 |
| 本系统角色 | 通过跨应用授权矩阵间接管 | ✅ 直接绑定/解绑 client 级角色 |
| 跨系统权限 | ✅ 跨应用授权矩阵（用户 × 应用） | ❌ 看不到别的系统 |
| 菜单可见性 | ✅ 全应用菜单权限点授权 | ✅ 仅本系统菜单**减法**（只能减不能增） |
| 账号映射 | ✅ 统一身份 ↔ 各系统本地账号 | 只读 |
| 新建用户 | ✅ 建即得平台身份 | ✅ 委托中心建 + **自动加入本系统**（便利入口，数据仍落中心） |
| 重置密码 | ✅ 允许（平台超管职责） | ❌ **移除**（密码是全局身份属性，应用管理员不得改他人在所有系统的密码） |
| 删除 | ✅（墓碑，用户名不可复建） | ❌ 改为「移出本系统」= 解绑本应用全部角色，身份保留 |

**设计理由（为什么不合并成一个）**：
1. **职责不同**：身份的生老病死是全平台事务，成员的进退是本系统事务。合成一个会让应用管理员拿到平台级删除权。
2. **符合使用习惯**：应用管理员只想"给我的系统加个人"，不该先学平台角色体系；平台管理员要"看这人能进哪些系统"，不该逐个应用去点。
3. **扩展性**：未来加"用户组/部门""数据行级权限"，都只需在中心侧加维度，应用侧面板不动；新应用接入即得一套完整成员管理（Level 3）。
4. **安全边界**：应用侧"移出本系统"而非"删除"，保证身份不因单点误操作消失。

### D-3：中心管理台归属 —— 保持寄生 portal，但明确标注为平台级

- **决策**：不新建 auth-console 前端应用。中心管理台继续由 portal `/portal/admin` 承载，但页面标题/面包屑/说明文案必须明确「MarsChat 统一认证中心 · 平台管理台」，与 portal 自身的 `/portal/users`（本系统用户）**并列且区分**。
- **理由**：portal 本身就是"一个入口掌控所有内部系统"的工具看板，承载平台管理符合其定位；新建前端要付出新应用注册、nginx、流水线、域名路径的持续维护成本，收益不抵。
- **代价**：portal 同时是"业务应用"和"平台宿管"，需靠 UI 标识与文档反复强调。
- **回滚/演进**：若未来 portal 下线或职责冲突，可把 `/portal/admin` 整体迁到独立 `auth-console`（组件是同一套，迁移成本≈新应用接入成本）。

### D-4：补齐 activecode 权限点上报 + 严格"每应用至多一个 public 落地页"

- activecode 新增 `menu-registry.yml`（client-id 以中心实际注册值为准），菜单覆盖真实页面，**有且仅有一个**标 `public: true`（踩过的坑 #17：strict 下没 public 菜单 → 普通用户登录后菜单全空）。
- cosmic 的 `MENU_REPORT_SECRET` 必须注入，否则权限点不上报（D7）。

### D-5：非自研系统

**结论：无法接入，且明确不接入。** 非自研系统无法改其代码（也禁止改），因此不可能让它的账密/会话走我们的中心。仅当目标系统原生支持 OIDC/SAML/LDAP 时，才可能以"标准协议对接"方式纳入（把 auth-center 当作 IdP），这属于未来可选项，不在本 ADR 范围。

## 3. 考虑过的其它方案（及否决理由）

| 方案 | 否决理由 |
|---|---|
| 各应用保留本地密码，中心只同步一份副本 | 密码改一处不同步，仍然是两套真源；违反 D-1 的根因诉求 |
| 取消独立登录，强制全部走 SSO 跳转 | 用户明确要求"自研应用也支持独立登录"；且中心抖动时全部应用不可登 |
| 中心管理台独立成 auth-console 前端 | 新增应用/部署/域名/流水线成本，portal 天然是平台门户（见 D-3） |
| 应用侧也允许删除用户 | 删除的是平台身份，属中心职责；应用侧应为"移出本系统" |
| 应用侧保留重置密码 | 密码是全局身份属性，改它会影响该用户在所有系统的登录，必须平台级权限 |

## 5. 后果与取舍

- ✅ 收益：账密与身份单点归一；新增用户一次建档全平台可用；应用侧面板零成本复用。
- ⚠️ 取舍 1：所有应用的登录**强依赖**中心可用性（fail-closed）。SSO 本来就是强依赖，故未恶化。
- ⚠️ 取舍 2：本地影子表仍然存在（承载业务外键），需长期保证不回潮成鉴权源 —— 靠代码注释 + 本 ADR + 手册三重声明。
- ⚠️ 取舍 3：中心管理台寄生 portal（D-3 已论证）。

## 6. 回滚

- 单应用回滚：`git revert` 对应 commit → 单目标流水线重部署，本地原校验逻辑仍在（未删除，仅停用）。
- 全平台回滚：不适用（本 ADR 是收敛而非切换开关）。
