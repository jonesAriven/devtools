# ADR-2026-10-22-R18：GR 单主固化四项收口执行（T-DEC-5 闭环）

- **状态**：✅ 已执行并全量验收（2026-10-22 20:26–21:10 CST）
- **授权**：良哥原文「1、2 做，3 选 A，4 也做」（对 R17 收敛的 T-DEC-5 四项）
- **前置**：`ADR-2026-10-22-R17-GR单主固化残留取证与待拍板.md`（取证）；`ADR-2026-10-21-MySQL-GR切单主.md`（切单主既定决策）
- **影响面**：MySQL GR 三节点（node1 105:3306 / node2 182:3307 / node3 182:3308）——全平台写路径；执行窗口约 45 分钟，其中写中断仅 node1 重启的 ~15s（Paxos 选主）+ set_as_primary 数秒

## 1. 背景（为什么必须收口）

R17 只读取证发现三处「配置文件与运行时不一致、被 persist 掩盖」的残留，全部构成**重建/重启类操作的雷**：

1. 全部 5 个配置文件 `group_replication_enforce_update_everywhere_checks=ON` 与单主模式相悖（官方 MySQL 8.0 文档 §20.1.3.1/§20.9.1：单主必须 OFF；joiner 值与组不符**无法入组**）——当前仅靠三节点 mysqld-auto.cnf 的 persist OFF 兜底 ⇒ **数据卷全新初始化、或按 ADR-2026-10-21 §4 纪律执行 RESET PERSIST 后重启，节点将无法入组**（上游 ADR 自带的整改动作在当时配置下会弄坏集群）；
2. node1 `start_on_boot=OFF`（T-ENG-14 的 ON 修复在 10-20 12:23 配置重写时被回退）⇒ 唯一写入点重启后不自动入组（T-ENG-13「孤立但可写」形态）；
3. node2/3 运行挂 182 本地 my.cnf、不读共享 node2/3.cnf，且两份副本内容已不一致（T-ENG-14 未修项）；182 的 debian compose 指向共享副本——下次重建将静默改变行为。

## 2. 执行内容

### 2.1 备份（全部可回滚）

| 对象 | 备份 |
|---|---|
| 共享 `cluster.cnf` / `node2.cnf` / `node3.cnf` / `docker-compose.mysql-cluster.debian.yml` | `*.bak-20261022-tdec5`（同目录） |
| 182 本地 `platform-mysql-{2,3}/my.cnf` | `my.cnf.bak-20261022-tdec5`（与既有 `.bak-20261020` 并存） |

### 2.2 项1：enforce=ON→OFF（5 个配置文件）

- `cluster.cnf`（node1）：sed 精确替换 `group_replication_enforce_update_everywhere_checks = ON` → `OFF`；
- `node2.cnf`/`node3.cnf`（共享）：按 182 本地**运行真相**整体重写——本地文件即验证过的现行配置，重写仅改 enforce 一处（`start_on_boot=ON`、`plugin_load_add`、`user=mysql` 等原样保留），行尾统一 LF；
- 182 本地两份 my.cnf：enforce 同步改 OFF 后**被软链替换**（见 2.4），本地文件退场为备份。
- 规范化 diff（去注释/空行/行尾）守卫校验：两节点均**仅 enforce 一行差异**才放行后续操作。

### 2.3 项2：node1 start_on_boot OFF→ON

- `cluster.cnf` sed 替换；三节点口径统一为 ON（node2/3 经 2.4 的共享副本同步后亦为 ON）。
- **已知代价（接受并记录）**：整机冷启（三容器同时起）时无引导者，需人工按官方 20.5.2 流程引导一次（mysql-gr-ops §2 纪律）；**节点级 `docker restart` 不受影响**——本轮三节点逐个重启全部自动入组成功。

### 2.4 项3（方案 A 降险变体）：node2/3 挂载对齐共享真源

**为何不用「docker rm + docker run 同参重建」**：参数复制（env / security-opt=apparmor:unconfined / 卷名 / healthcheck）出错面大于收益；且 `docker restart` 本就会重新解析 bind mount 源路径（内核态），软链方案即可让容器读到共享文件——**后用进容器 cat 实证**。

**为何绝不能用 debian compose 直接 up**：该 compose 的 `volumes:` 声明 `platform-mysql-{2,3}-data: driver: local`，带 `-p mysql-cluster` 项目前缀后会创建 `mysql-cluster_platform-mysql-{2,3}-data` **空卷**，而实际运行卷名为 `platform-mysql-{2,3}-data`（当年 docker run 创建、无 compose 标签）⇒ 直接 up = 挂空卷 + 初始化全新 datadir。**已拆**：`driver: local` → `external: true`（复用现有卷；缺卷时 compose 直接报错而非静默新建）。

**实际执行**：
1. 共享 `node2/3.cnf` 按本地运行真相重写（2.2）；
2. 182 本地 my.cnf → 绝对软链 `→ /mnt/shared/platform/mysql/node{2,3}.cnf`；
3. debian compose 拆空卷雷（volumes 改 external）；其 my.cnf 挂载本就指向共享 ⇒ **compose 路径与运行路径从此同源**。

### 2.5 项4：RESET PERSIST + 顺序重启

1. 三节点 `RESET PERSIST`（persisted_variables 立即归 0；mysqld-auto.cnf 仅剩 `{"Version": 2}`）；
2. 按 **node2 → node3 → node1** 逐个 `docker restart`，每步轮询至 SECONDARY ONLINE 再动下一个（严禁同时重启——官方 20.5.2 / mysql-gr-ops §2：全量 ON 无引导者会全失败）：
   - node2 / node3 重启：try1 即入组，node1 保持 PRIMARY，**写零中断**；
   - node1 重启：离开后约 15s 内 node2(182:3307) 经 Paxos 自动当选 PRIMARY（**写中断仅此窗口**，应用侧 Connector/J 三地址 / cosmic DB_HOSTS failover 自动接管）；node1 以 SECONDARY 回归；
   - 纠偏：`SELECT group_replication_set_as_primary('<node1 uuid 09a2a7b2-...>')` 切回 node1——避免写长期落在磁盘 93% 的 182；`member_weight=60` 使后续选举仍偏好 node1。

## 4. 执行期两个事件（如实记录，供防复发）

1. **自造 bug 被守卫抓回**：重写 node3.cnf 时误抄 node2 的 `port = 3307`（node3 应为 3308）——若不修正，node3 重启时将抢 3307 端口直接起不来。grep 复核时发现，sed 修正后才进入重启流程。**教训：模板化重写配置文件后，必须逐节点 grep 关键差异行（port / server-id / local_address）**。
2. **CRLF 误报**：182 本地 my.cnf 为 CRLF（Windows 遗留）、新写共享文件为 LF ⇒ 首轮 diff 报「32 行全异」，守卫正确拦下软链替换；`tr -d '\r'` 规范化后确认仅 enforce 一行差异才放行。**教训：跨 Windows/Linux 作者环境的配置比对，先规范化行尾**。（MySQL 对两种行尾都能正常解析，属比对工具问题而非配置问题。）

## 5. 遗留注记

1. **CIFS 依赖**：182 的 `/mnt/shared` 是 CIFS（`//192.168.31.77/ideaworkspace`，soft 挂载）——node2/3 的配置读取从此依赖该网络共享可用性（node1 本就如此，风险既有且一致）；若 77 宕机，节点重启将读不到配置。
2. **运行容器与 compose 的差异项**：运行中 node2/3 无 healthcheck、无 mem_limit（debian compose 声明 512m + healthcheck）——保留运行现状未动；将来若按 compose 重建会获得这两项（属预期增强，非本次范围）。
3. **留用脚本**：182 `/root/verify_tdec5.sh`（规范化 diff + 软链守卫）、`/root/gr_wait.sh`（成员状态轮询）——可复用，非一次性探针。
4. **回滚路径**：任一环节可还原——删软链还原本地 my.cnf 备份（`.bak-20261022-tdec5`）+ 共享四文件备份还原 + `docker restart`；集群数据全程未动（仅配置与重启）。
