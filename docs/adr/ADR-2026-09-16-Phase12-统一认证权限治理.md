## 1. 背景

### 1.1 用户初衷（Phase 11 已确立，本轮不变）

1. **统一登录**（一处登录、处处可进）· **统一鉴权**（权限判定同源）· **用户统一管理**（一处建号、全平台可用）· **权限统一管理**（权限点与授权集中）· **账号映射**（本地账号 ↔ 中心身份）。
2. **自研应用接入只需「接公共组件 + 配置」**（`apps-registry.yml` 单一真源 + 手册 Level 0-3 分层指南）。
3. **非自研系统禁止改其代码**，故不接入（仅当目标系统原生支持 OIDC/SAML/LDAP 时，才可能以标准协议把 auth-center 当 IdP 纳入）。
4. **超管邮箱 `marschat@163.com`**（平台 superadmin + 6 应用 client admin）。
5. **登录方式**：账密 / 邮箱验证码 / 忘记密码。

### 1.2 第 4 点诉求原文（本轮核心命题）

> 「每个系统是不是应该有自己的用户管理菜单，然后统一认证登录系统是不是也应该有个用户管理菜单。这两个菜单功能应该是不同的……如何设计好，如何设计更符合使用习惯、更健全、功能扩展性更强。」

### 1.3 本轮复核发现了什么 —— Phase 11 的收口结论被高估

Phase 11 的「账密真源归一」确已落地（Phase 11 D1-D5 成立），但**「用户统一管理」「权限统一管理」两个初衷的收口质量参差**。本轮按「只信代码与配置、不信任任何历史结论」全量复核，得 5 条结论：

| # | 结论 | 严重度 |
|---|---|---|
| C1 | **「应用管理员」这一角色在服务端根本不存在**：auth-center 所有 `/admin/**` 端点类级只有 `@PreAuthorize("hasRole('ADMIN')")`（平台管理员）；`client=xxx` 只是**查询过滤参数**，不是权限边界 | 🔴 P0 |
| C2 | 推论：**能打开任一应用「本系统用户」页的人，必然是平台管理员**，因此天然能 `DELETE /admin/users/{id}`、`PUT /admin/users/{id}/password` 操全平台用户。「应用侧只能管本系统」是错觉 | 🔴 P0 |
| C3 | 应用 BFF 多为**前缀全透传** `/admin/**`（activecode / cosmic / infra-monitor），中心每加一个 `/admin` 端点，应用侧零改动即可触达 —— 边界只会越来越松 | 🔴 P0 |
| C4 | P0-4 根因与 C1/C2 同源：kb-web / kb-ops 的「应用令牌」**就是**中心令牌（登录路由 `/kb/api/auth/** → lb://auth-center`），故它既能调本应用 API，也能调中心 `/admin/**` | 🟠 P1 |
| C5 | activecode `WebMvcConfig` 把 `POST /activation/generate`、`POST /activation/verify`、`GET /config/default-expire` **整个排除出鉴权**（匿名）；其余 7 个写接口**只验登录、不验权限** | 🔴 P0 |

### 1.4 一句话根因

> **Phase 11 的两类菜单职责切分（D-2）只在 UI 层成立 —— 组件参数 `scope.mode='app'` 藏起了按钮，但平台级写端点对应用侧依然敞开。**
> 「应用侧不能删人、不能重置密码」是**前端约定**，不是**服务端边界**。

证据：
- `auth-center/.../controller/AdminUserController.java:22` —— 类级 `@PreAuthorize("hasRole('ADMIN')")`，覆盖全部 5 个端点；`AdminRoleController.java:25`、`AdminAuthzMatrixController.java:52`、`AdminAppClientController.java`、`AdminAccountMappingController.java`、`AdminAuthzPolicyController.java` **同一鉴权面、同一条规则**。
- `AdminUserController.java:41-51` —— `list()` 的 `client` 参数只决定走 `listForAdminScoped(client,...)` 还是 `listForAdmin(...)`，**同一端点、同一权限**；`AdminRoleController.java:83-107` 的 `?client=` 同样只是参数，无「调用者是否有资格改这个 client」的校验。
- 全仓 `grep`「应用管理员 / appAdmin / isAppAdmin」→ **0 命中**。
- `active-manager/.../controller/AdminProxyController.java:76` —— `@RequestMapping("/activecode/api/admin/**")` **前缀全透传**（注释 `:48-49` 明说「中心每新增一个 `/admin/**` 端点，消费方零改动即可用」）。
- `cosmic-studio/app/routers/auth.py:565-659` —— `_center_proxy` 逐端点声明了 `PUT /users/{id}`、`PUT /users/{id}/password`、`DELETE /users/{id}`，门槛只有 `require_permission("api:admin:write", min_role="admin")`（**cosmic 本地角**）→ 同样的越权面。
- `active-manager/.../config/WebMvcConfig.java:50-52` —— 三个端点匿名；`AuthInterceptor.java:24-30` —— 只判 `session.loginUser != null` 就 `return true`，**无任何权限判定**；`menu-registry.yml:60-72` 上报的 6 个 api 点全仓 **0 消费**。

## 2. 决策

### D-1：把「身份 / 成员 / 授权」三层**下沉到 API 边界**（C1–C4 的共同根因，一处修复覆盖全部）

```
┌── Identity 层（身份）──────── 仅平台管理员 (ROLE_ADMIN)
│     管：人是否存在、口令、全局角色、停用/删除墓碑、账号映射、跨应用总览
│
├── Membership 层（成员）──── 应用管理员（本 client 的 api:admin:write）
│     管：谁在本系统、在本系统什么角色、移出本系统
│
└── Entitlement 层（授权）
      ├ 平台级：角色 → 权限点（角色授权矩阵）……… 仅平台管理员
      └ 应用级：用户 → 应用角色 / 菜单减法 …………… 应用管理员（限本 client）
```

**判据（服务端如何认定「应用管理员」）**
- 新增 `PermissionService.isAppAdmin(long userId, String clientId)`，口径取 **A**（复用已有权限点）：该用户在该 client 下持有 `api:admin:write`。原料即 `computeForUser(userId, clientId)`（`PermissionController.java:42` 已在用）返回的 `permissions` 集合；与 cosmic BFF 现有门槛口径一致（`cosmic-studio/app/routers/auth.py:544` `require_permission("api:admin:write", min_role="admin")`）——**语义已存在，无需新概念**。
- 新增闸门 Bean `auth-center/.../security/AppAuthzEvaluator.java`（Spring Bean 名 `appAuthz`），供 SpEL 调用：平台管理员天然放行；否则调 `permissionService.isAppAdmin`。调用者 uid 从 `SecurityContext` 取（`JwtAuthenticationFilter` 已设 `principal=uid`）。

**新增端点（Membership 层，客户端强制注入）**

| method | path | 鉴权 | 落库（复用已有） |
|---|---|---|---|
| GET | `/admin/clients/{clientId}/members` | `@PreAuthorize("@appAuthz.isAppAdmin(authentication,#clientId)")` | `userService.listForAdminScoped(#clientId,...)` |
| POST | `/admin/clients/{clientId}/members` | 同上 | `permissionService.assignUserClientRoles(#userId,#clientId,#roleIds,operatorId)` |
| DELETE | `/admin/clients/{clientId}/members/{userId}` | 同上 | `assignUserClientRoles(#userId,#clientId,Set.of(),operatorId)`（空集＝移出本系统） |

**Entitlement 层应用级只做「菜单减法」**：应用管理员只能发 `menu-overrides`（在平台已授予角色的范围内**扣除**），**不能**给角色新增权限点 —— 那是平台级 `roles/{roleId}/permission-codes`（保持 `hasRole('ADMIN')`）。这是**防应用管理员自我提权**的关键红线。

**理由**：
1. **越权在 API 层被堵死**，UI 隐藏退化为第二道而非唯一一道防线（C2 直接被消灭）。
2. **应用侧 BFF 只需代理 `/members/**`**，天然带 client 绑定，不可能误操作他应用的用户（C3 根治）。
3. **不需要新表**：`listForAdminScoped`、`assignUserClientRoles`（**已含审计留痕** `user.client_roles` / `user.remove_from_app`）、`userClientRoleIds`、`computeForUser`、`OperationLogService` 等资产全部现成（详见 `p12-architect-design.md` §1.1④）。
4. **语义清晰**：「添加已有用户到本系统」= `POST /admin/clients/{cid}/members {userId}`；「移出本系统」= `DELETE .../members/{userId}`，与「删除身份」彻底解耦。
5. **扩展性**：未来「用户组/部门」＝Membership 主体扩展为 `{type:user|group}`；「数据行级权限」＝Entitlement 加 `type=data`；「邀请制」＝Membership 创建路径的变体；「审计」＝横向能力。**四种扩展都不需要重构三层**（`p12-architect-design.md` §2.5）。

### D-2：`client_id` 从 URL **path** 取，不从 body/query 取（服务端强制注入）

只要 client 是「参数」，应用 A 的管理员改 `client=B` 就能越界；把它钉进 path 并在服务端强制注入，越界在**路由层**就不成立。

三条实现要点：
1. `clientId` 只存在于 `@PathVariable`；**不接收** body/query 里的 `client`（若历史 body 带 `client`，服务端**忽略并覆盖**为 path 值）。
2. `AppAuthzEvaluator.isAppAdmin` 校验的 clientId 与 Service 落库用的 clientId **必须是同一个 `#clientId` 变量**（同一次方法调用，杜绝「鉴权用一个、落库用另一个」）。
3. 应用 BFF 透传时把 `clientId` 拼进 path（例如 kb-web 的 `baseUrl` 应为 `/kb/api/admin/clients/marschat-kbweb/members`）。

**理由**：**纵深防御**。D-1 让应用管理员不再是平台管理员，D-2 再保证即便将来某个客户端越权构造请求，也越不出自己的 client。二者缺一，边界都不完整。

### D-3：两类用户管理菜单 —— **中心台管「人」，应用台管「关系」**

- 中心「统一认证中心 → 统一用户」＝**人的档案 + 平台级授权**（创建、停用、删、改密、跨应用矩阵、账号映射）。
- 应用「本系统用户」＝**人与本应用的关系**（有没有账号、在本系统什么角色、在本系统看得到哪些菜单）。
- **应用台不创建人**（人属于平台）：要加人＝「添加已有用户」或「邀请成员」。

**功能对照（关键差异）**

| 功能项 | 中心平台管理台（scope=platform） | 应用「本系统用户」（scope=app） |
|---|---|---|
| 查看用户 | ✅ 全平台列表（`GET /admin/users` 不带 client） | ✅ 只列本系统（`.../members`，服务端 `listForAdminScoped` 强制过滤） |
| 新建用户 | ✅ 表单：username/password/全局 role/nickname/email | ❌ **无**（改为「添加已有用户」/「邀请」） |
| 邀请 | ✅ 可按邮箱发邀请（**预留**） | ✅ **主力动线** |
| 停用 / 启用 | ✅ 全局 status | ❌ 无（停用是全局动作，属平台） |
| 移出本系统 | ✅ 经矩阵改绑 | ✅ **主力** |
| 重置密码 | ✅ | ❌ **无**（口令属身份层） |
| 删除（墓碑） | ✅ | ❌ 无 |
| 全局角色绑定 | ✅ 改 `user.role` | ❌ 无 |
| 应用角色绑定 | ✅ 矩阵单元格改绑 | ✅ **主力**（本系统 roles，`roleIds` 覆盖） |
| 建应用角色 | ✅ `POST /admin/clients/{clientId}/roles` | ❌ 无（防自造角色提权） |
| 菜单授权 | ✅ 角色→权限点（平台级） | ✅ **仅减法**（menu-overrides） |
| 账号映射 | ✅ 全量 + 手工认领/解绑 | ⚠️ 只读本应用 |
| 跨应用总览 | ✅ 授权矩阵（行=人，列=应用） | ❌ 无 |
| 审计日志 | ✅ `GET /auth/log/list`（全局） | ⚠️ 只读本应用相关 |

**UX 主张（应用管理员「加个人」的动线）**：入口「+ 添加用户」→ 搜中心已有用户（username/email/nickname）→ 选「本系统角色」（多选，取自本应用 `scope=client` 角色）→ 落库 `POST .../members`。校验：未选人禁用确定；角色至少选 1；已在本系统者置灰标「已在本系统」。失败文案按中心 `message` 原样透传（403 →「你没有本系统的用户管理权限，请联系平台管理员」）。**「邀请新建」为 Phase 13 预留**（新表 `invitation`：email/client_id/role_ids/token/status/expires_at），现在先把接口形状定下来，避免未来改成员层签名或各应用自造邀请。

**理由（为什么不合并成一个菜单）**：
1. **职责不同**：身份的生老病死是全平台事务，成员的进退是本系统事务。合成一个会让应用管理员拿到平台级删除权（正是 C2 的病根）。
2. **符合使用习惯**：应用管理员只想「给我的系统加个人」，不该先学平台角色体系；平台管理员要「看这人能进哪些系统」，不该逐个应用去点。
3. **扩展性**：三层切分对四种未来能力（用户组/行级权限/邀请/审计）**都不需重构**，只需在层内加类型。
4. **安全边界**：应用侧是「移出本系统」而非「删除」，身份不因单点误操作消失。

### D-4：闸门落位 —— 管理面统一在 auth-center，业务面落应用侧；**判定真源唯一在中心**

| 面 | 落位 | 载体 | 判定真源 |
|---|---|---|---|
| **管理面**（`/admin/**`：身份/成员/授权） | **统一在 auth-center** | `@PreAuthorize`（类级 + `@appAuthz`） | 中心库（DB `user.role` / `sys_user_role` / `sys_permission`） |
| **业务资源面**（各应用自身写接口，如 activecode `/activation/**`） | **应用侧** | `HandlerInterceptor`（MVC）/ `GlobalFilter`（WebFlux，kb-gateway 已有） | 中心 `GET /auth/permissions` 返回的权限点（应用**不复制**角色体系） |

**理由**：
1. 全部管理端点的判定所需数据（`sys_user_role`/`sys_permission`/`sys_role`）**全在中心库，应用侧没有**；强行在 6 个应用各抄一份＝改一处漏 5 处（历史教训见 `kb-web/src/utils/token.ts:8-10` 注释）。
2. 应用 BFF 已确立「不复制平台角色判定、原样透传状态码」的取舍（`AdminProxyController.java:43-45`），沿用之。
3. **业务面无法放中心**：activecode 的写接口（`/activecode/api/activation/**`）由 active-manager（`192.168.31.182:18080`）承载，**请求根本不经过 auth-center**，故闸门只能在应用侧。又因 activecode 是 **Spring MVC**（`AuthInterceptor implements HandlerInterceptor`），**不能直接照抄** kb-gateway 的 WebFlux `GlobalFilter`，需以 `HandlerInterceptor` 载体实现同范式（`p12-architect-design.md` §4.2）。
4. 两者不重叠：`api:admin:write` 权限点**同时**被 kb-gateway `PermissionAuthzFilter`（拦业务写接口）与中心 `AppAuthzEvaluator`（判应用管理员）消费 —— **同一权限点、两处消费，是设计一致而非重复**。

> ⚠️ **与「管理层统一放中心」的关系**：D-4 的「统一放中心」**指管理面**。（本条澄清 team-lead 任务书对「P0-3 闸门统一放 auth-center Controller」的表述 —— 经复核，P0-3 的 activecode 业务闸门**只能**落应用侧，原因见理由 3；但**判定真源仍唯一在中心**，符合「统一」的实质。）

### D-5：P0-4 拆 A / B —— 先同源化，令牌分离另立专项

| 子项 | 内容 | 时机 |
|---|---|---|
| **A 同源化** | `/admin` 调用一律走**同源 BFF**：kb-web 走 kb-gateway 新增路由（`Path=/kb/api/admin/**` → `lb://auth-center`，`StripPrefix=2`）；kb-ops 新增 Servlet BFF；两个 `UsersView.vue` 的 `baseUrl`/`appRoles.baseUrl`/`issuer` 改相对路径。**浏览器不再跨域直连中心** | **立即可做** |
| **B 令牌分离** | 网关/应用自签**应用令牌**，中心令牌只落服务端（Redis/内存），调 `/admin/**` 时网关用 `CenterTokenRelayFilter` 取回中心令牌注入 | **Phase 13 专项，需良哥拍板** |

**B 的风险/成本（须登记）**：① 网关现在已同时支持「中心 HS256 legacy」与「中心 RS256」两种验签，再加「网关自有密钥」＝**三种并存**，验签分流回归面大；② 中心令牌改由 Redis 持有 → 网关多一份状态（现为纯无状态转发），引入 Redis 故障降级路径；③ 影响面＝kb-web + kb-ops **全部 API 调用**（不只管理页），属枢纽改动，须先走 `appmap.py impact`。

**务实判断**：真正把「令牌危险度」降下来的是 **D-1**（让应用管理员不再持有 `ROLE_ADMIN`）。D-1 + D-5-A 组合后，localStorage 里那把令牌的破坏力从「能删全平台用户」降到「能调本应用 API」，**B 的紧迫性显著下降** —— 先做 D-1 与 A，再评估 B 是否需要。

### D-6：P0-3 —— activecode 匿名洞收敛 + 补业务闸门

- **规则表**（放 `application.yml`，与 kb-gateway `authz.rules` 同构）：
  `POST /activation/generate → code:generate`；`DELETE /activation/{id} → code:delete`；`DELETE /activation/batch → code:batch-delete`；`PUT /activation/{id}/alias → code:alias`；`PUT /activation/config/default-expire → config:expire`；`PUT /activation/version-check → config:version-check`。（`batch` 规则须排在 `*` 之前。）
- **判定语义**（与 auth-core / kb-gateway 同一套）：`enabled=false` 全放行（回滚开关）→ `OPTIONS` 放行 → 非写方法放行 → 规则未命中放行 → 命中则取**用户本人**中心令牌（无 → 401）→ 调 `GET /auth/permissions?client=marschat-activecode`：`configured=false` 放行（R10）、平台角色 `admin/superadmin` 放行、含所需全码放行，否则 **403** → 中心不可达按 `failOpen`（**默认 false = 拒绝**，fail-closed）。
- **匿名洞**：从 `WebMvcConfig` 的 `excludePathPatterns` **移除** `/activation/generate` 与 `/activation/config/default-expire`（至少过 `AuthInterceptor` + `PermissionInterceptor`）。`/activation/verify` **暂保留匿名，待产品确认**（见 §7 待办）。

**理由**：与 kb-gateway 既定口径一致 —— 「接口＝动作，判定不了就不放行动作」（`kb-gateway/application.yml:201`）。activecode 是 6 应用中唯一「有权限点、零闸门」者（C5），最易被利用，纯收益、零依赖、可独立回归。

### D-7：加人动线的读权限**最小化例外**（对 D-1 的唯一豁免，仅「只读 + 字段最小化」）· 2026-09-16 追加

**背景**：D-3 规定应用台的主力争是「添加已有用户」——它**必须**能看到「尚未加入本系统的平台用户」才能选人。但 D-1 把 Identity 层（含 `GET /admin/users`、`GET /admin/roles`）定为**平台管理员专有**。若不处理，应用台加人动线在 D-1 落地后**不可用**（详见 `p12-menu-ux-spec.md` §8-1）。

**否决的做法（为什么不是直接放开 Identity 读）**：
- 直接允许应用管理员调 `GET /admin/users`（不带 client）＝ 应用 A 的管理员能看到**全平台所有人的邮箱、全局角色、状态** —— 信息面远超其职责（它只需要「把某个已存在的人加进来」）；
- 直接允许调 `GET /admin/roles` ＝ 暴露全局角色表与**其它 client** 的角色，等于把平台角色体系泄漏给每个应用管理员。

**决策：在 Membership 层新增两个受限只读端点，作为 D-1 的「最小化例外」**（已派 auth-center 实施）：

| method | path | 可达者 | 硬约束 |
|---|---|---|---|
| GET | `/admin/clients/{clientId}/member-candidates` | 应用管理员（`@appAuthz.isAppAdmin(authentication,#clientId)`） | ① **只返回 3 个字段**：`userId / username / nickname`（**禁 email / role / status**）；② **只列尚未加入本 client 的用户**；③ `keyword` **必填且 ≥2 字符**；④ `size` 服务端 **clamp ≤20**；⑤ **写审计**（复用 `OperationLogService`） |
| GET | `/admin/clients/{clientId}/roles` | 应用管理员（同上） | **只返回本 client 的角色**（`scope='client' AND client_id=#clientId`），**不暴露全局角色表** |

**口径边界（务必与 D-1 合并理解）**：
- Identity 层的「**管理写**」（建/停用/改密/删身份、改全局角色）**仍然仅平台管理员** —— 本条**不符权**；
- 本条豁免的仅是「**加人动线所必需的、最小粒度的只读**」，且叠加**四重收敛**：字段最小化 + 只列未加入者 + 强制关键词/分页 + 审计；
- 与 §1.5 的 `POST /admin/clients/{clientId}/roles`（**建角色，平台专属**）**同名不同权** —— 见设计规格 §1.5 的权限口径差异表。

**理由**：
1. **不违 D-1 的实质**：D-1 要防的是「应用管理员越权**改**全平台」，而非「读到一个待加入者的用户名」。把读面收敛到 3 字段 + 只列未加入者，越权价值趋零。
2. **加人动线必须可用**：否则应用台只能「移出」不能「加入」，功能残缺。
3. **有替代即最小**：若不设此例外而放开 Identity 读，泄漏面大 10 倍以上；两者相比此例外是**最小代价**。

> **D-3 功能表联动**：D-3 表「查看用户（应用侧）」应读作 `.../members`（列**已加入**者）+ `.../member-candidates`（搜**未加入**者），二者共同构成应用台的用户可见面。

## 4. 复核误判与纠偏（本轮教训，如实记录，不美化）

> 本轮团队出现**四次判断偏差**（任务书点名两次：clients.yml / `/root/auth-center` 分叉；另两次为本轮架构师**静态复核自身**的偏差：cosmic 上报 / kb-web 菜单路径，一并如实记录）与**一次工程事故**。核心教训与 Phase 10→11 一致：**只验链路/静态代码会错，必须以线上实测或源码实读为准**。

### 4.1 纠偏 ①：「auth-center 源码里没有 `clients.yml` / `ClientsYmlLoader`」—— **误判，实际在**

- **前判**：审查 auth-center 源码目录，未见 `clients.yml` 与 `ClientsYmlLoader`，据此怀疑配置真源机制失效。
- **纠偏（线上 jar 内实测，决定性）**：`docker exec auth-center unzip -l /app/auth-center.jar` 实测到 `BOOT-INF/classes/clients.yml`（**6110 B**）与 `BOOT-INF/classes/com/marschat/authcenter/config/ClientsYmlLoader.class`（15259 B）—— 二者**都在 jar 里、都在生效路径上**。
- **误判根因**：把 `/app` 目录（`docker inspect` 显示**只有** `auth-center.jar` 83,369,211 B、无 bind mount）当成了检查对象，误以为「目录里没有＝工程里没有」。**正确做法是解包 jar 看 `BOOT-INF/classes/`**。

### 4.2 纠偏 ②：「`/root/auth-center` 与上游分叉」—— **误判，不是分叉，是落后 45 提交的陈旧克隆**

- **前判**：服务器 `/root/auth-center` 的 `git branch -vv` 显示 `main be405b4 [github/main: 领先 2]`，据此判「本地与上游分叉」。
- **纠偏（GitHub Compare API 实测）**：`GET /repos/jonesAriven/auth-center/compare/main...be405b497095…` → **`status="behind", ahead_by=0, behind_by=45`**（`compare/main...3bf3474…` → `behind_by=47`）。`be405b4` 与 `3bf3474` **都是上游 main 的祖先**；`git branch -a --contains be405b4` 显示其提交**也已在上游 main 里**。
- **误判根因**：该克隆的**本地 remote-tracking 引用 `github/main` 停在近 50 个提交前的 `3bf3474`**，导致 Git 误报「领先 2」。**这不是真分叉，纯粹是陈旧引用造成的假象。**
- **结论**：改代码**不要用 `/root/auth-center` 比对**（它是旧世界），真正可用的源 = `github.com/jonesAriven/auth-center` main（Woodpecker `clone_url`）。

### 4.3 纠偏 ③（架构师本轮静态复核的偏差）：「cosmic 权限/账号上报从未工作」—— **不成立，实测本已在运行**

- **前判（本轮架构师审计 `p12-architect-audit.md` §A.1⑥ = D7）**：`app/menu_report.py` 的 `MENU_REPORT_SECRET` 默认空 → 判定「cosmic 的权限点实际上报仍被跳过，中心侧无 cosmic 权限点」。
- **纠偏（线上 MySQL 实测，`p12-engineer-fix.md` §3.1）**：`sys_app_client` 中 `cosmic-studio` `status=1`、`last_sync_at=2026-09-16 00:11:57`、`secret_len=32`、`menu_json_len=1770`；`sys_permission` 中 cosmic-studio **19 个权限点**；`app_account_mapping` 中 cosmic-studio **3 行** → **cosmic 上报链路本来就在正常运行**。
- **误判根因**：**静态审计读不到部署环境注入的 secret**（`MENU_REPORT_SECRET` 由运行环境注入，非代码默认值）。静态复核只能证明「代码存在 fail-soft 分支」，**不能证明线上是否走到该分支**。
- **修正后的真实缺陷**：真缺陷是**配置真源缺键** —— `devtools/apps-registry.yml` 的 `cosmic-studio` 条目缺 `menu-report-secret` 字段（对比 kbweb/inframon/activecode 都有），→ 在「**换机器/重建环境**」场景下会因 `MENU_REPORT_SECRET` 空而 **fail-soft 静默降级（不上报、不报错）**。已在 `27ca74d` 补齐（env-only）。

### 4.4 工程事故与处置：Windows 本地 devtools `.git` refs 被清空

- **现象**：Windows 本地 devtools 克隆出现 `git rev-parse HEAD` 失败、`branch dev` 无任何提交、约 **2012 个文件被 staged**（含 `.playwright-browsers/chromium-1223/**`，本应被 `.gitignore` 排除）；连同 `docs/adr/INDEX.md` 一起 `M`，与自动备份进程的交叠使 **P0-1/P0-3 的本地提交一度丢失**。
- **处置**：靠 **fetch 远端 + 手写 ref 文件 + 重建 index** 恢复；随后 `.git` 再次被 `gc --prune` 清掉未推送对象，改为**在服务器（mykng `/root/devtools`）完成提交 + 推 Gitee，再镜像到 GitHub**（`fetch origin dev` → `push github FETCH_HEAD:refs/heads/dev`）。
- **根因（两因叠加）**：
  1. **本机 `.git/refs` 不落盘痼疾**（历史遗留，会话结束后 refs 目录丢失）；
  2. **自动备份 cron 每 10 分钟 `git add -A` + commit + `pull --rebase` + push** —— 与开发进程争抢 `.git/index.lock`，`add -A` 把禁区文件（`.playwright-browsers/**`）一并 staged，`gc --prune` 清掉未推送对象。
- **处置结论**：Windows 侧**不做** commit/push（沙箱亦拒绝 `.git` 写操作）；**该损坏仍在**，须由团队/自动备份负责人确认是否先停 auto-backup 再重建（见 §7 待办）。

### 4.5 纠偏 ④（架构师审计 P2-6 的偏差）：「kb-web 菜单路径与路由不一致」—— **误判，非缺陷**

- **前判（`p12-architect-audit.md` §B.2 问题 5 的 P2-6）**：`menu-registry.yml` 登记的 path 是 `/users`，而「实际路由是 `/settings/users`」，判为「菜单路径与路由不一致」的 P2 缺陷。
- **纠偏（源码实读，`p12-menu-ux-spec.md` §8-5）**：`mykng/kb-web/src/router/index.ts:128` 的路由 `path:'users'` 与 `:120` 的 `settings` **同级**（`settings` 是**叶子路由**、不是带 `children` 的父路由），故实际路由 = `/{ctx}/users`，与 menu-registry 的 `/users` **一致**。`views/settings/UsersView.vue` 里的 `settings/` **只是文件目录归属**，不是路由层级。
- **误判根因**：**把文件目录当成路由层级**（`views/settings/` → 误推 `/settings/users`）。审计只比对了 `menu-registry` 与 `import` 路径，**未核对 router 的父子结构**。
- **处置**：审计报告该条**已标注「已澄清：非缺陷」**，**不留假待办**（假待办比漏项更消耗人）。

## 6. 后果与已知权衡

- ✅ **收益**：把两类菜单的职责切分从 UI 约定升级为 **API 边界**；越权在服务端被堵死；应用 BFF 天然带 client 绑定；三层切分对未来四种能力扩展**零重构**。
- ⚠️ **权衡 1（必须登记）**：**前端守卫 fail-open，靠接口层 403 兜底**。SSO/权限探针失败时**不**拦用户（`kb-web/src/utils/sso.ts:98` 注释「探针异常一律保持现状，fail-safe」），避免中心抖动把在线用户全踢出去；管理页数据接口则 fail-closed（BFF 拿不到中心凭据/中心不可达 → 明确 401/502，不返回空列表冒充成功，`AdminProxyController.java:80-83,105-108`）。**此条与 repo-map 已有规则「fail-open 型前端守卫必须登记」一致**，登记于此。
- ⚠️ **权衡 2（运维风险，必须登记）**：**推 auth-center main 自动上生产，无审批门、无 `:previous` 镜像** —— `docker images` 只有 `kb-app-auth-center:latest`（在跑）与两个 legacy 镜像；`deploy.sh` 无回滚分支。**回滚只能 `git revert` + 再推一次重跑 CI**；若线上已坏需最快止损，只能靠事先手工留存的镜像 tag（当前**无留存**）。→ **改造前先 `docker tag kb-app-auth-center:latest kb-app-auth-center:rollback-<日期>`**。
- ⚠️ **权衡 3**：**OIDC 径无 token 版本校验（tv）**。`JwtAuthenticationFilter` 的 tv 版本校验与黑名单只覆盖 legacy 径（`:62-65`、`:104-110`），OIDC 径缺失 → 「删/停用后旧 token 仍可用」在 OIDC 会话下**存在窗口**，登记为已知缺口（R7）。
- ⚠️ **权衡 4**：**中心凭据暂存于进程内存**。infra `CenterSessionStore.java`、cosmic `routers/auth.py:221` `_oidc_tokens = {}`、activecode `CenterSessionStore` 均为进程内 Map → 应用重启/多副本/滚动发布即 401（D14 修完后新引入的**可用性单点**，属 P1-7）。
- ⚠️ **权衡 5**：应用侧「移出本系统」可被**超管例外**语义绕过（平台超管被移出后仍能凭身份重新进入，`AuthController.java:442-446`、`routers/auth.py:163-176`）→ UI 显示「已移出」属语义欺骗，需「显式拒绝名单/停用」能力（R3，P1）。
- ⚠️ **权衡 6**：`/activation/verify` 暂留匿名（待产品确认），在此期间它仍是公开端点。
- ⚠️ **权衡 7**：三层改造若落地，`?client=` 旧端点将保留一个发版周期（`@Deprecated`），期间旧攻击面**未完全关闭**。
