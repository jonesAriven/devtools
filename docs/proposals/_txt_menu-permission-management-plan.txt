先纠正一个前提
「很多自建应用没有菜单」——实测下来不成立。每个应用都有菜单，只是只有 cosmic 把它当作「数据」，其余全写死在 Vue 模板里（kb-web ~50 项、kb-ops-web ~25 项、infra-monitor-web ~11 项、myfrp 4 项）。所以问题不是「没菜单」，而是菜单以标签形式存在，无法被授权。把标签变成数据，就是菜单管理的全部前提。

两个实证细节：
① 三个前端路由文件里 meta 只有 requiresAuth，没有 title／icon／menu 任何元数据——菜单信息 100% 在模板标签里，路由与菜单是两套互不相干的东西。
② myfrp 的 <el-menu-item index="/users" v-if="role === 'ADMIN'"> 是全平台唯一的「菜单权限」雏形——硬编码在模板里，改一次要重发前端。

三、关键区分：菜单的三层
「菜单管理」这个词把三件不同的事混在一起了，必须先拆开，否则设计必然走偏。
层 | 管什么 | 归属 | 变更频率 | 
L0 菜单定义 | 
菜单树本身：key／标题／图标／路径／分组／排序／是否隐藏 | 
应用自己 | 
随应用发版（跟路由/页面强绑定） | 
L1 菜单权限 | 
谁能看到哪些菜单：角色 → 菜单、用户 → 菜单 | 
认证中心 | 
随时改（运营动作，不该发版） | 
L2 菜单渲染 | 
按权限过滤并渲染出侧边栏 | 
前端公共组件 | 
随组件发版 | 
为什么必须拆开：如果 L0 也放到认证中心，那么「给某个应用加一个菜单项」就要改认证中心的数据甚至代码，并重新部署它——又回到了上一份方案里「接入要动 8 处」的老问题。而 L0 天然属于应用：菜单项对应的是路由和页面组件，页面没发版，菜单先出现只会 404。
四、核心判断：菜单定义留应用侧，认证中心只存「授权」
A. 菜单全部集中到认证中心定义
好处：一处看全平台菜单。坏处：认证中心变成所有应用菜单的数据库——加菜单要动它、菜单与前端路由脱节（先有菜单后有页面就会 404）、还要为每个应用维护不同的菜单模型。这是把耦合从应用搬到了枢纽，不推荐。
B. 定义留应用侧，元数据上报，认证中心只存权限 ✅ 已拍板 2026-09-10
应用侧写 menu-registry.yml（L0）→ 启动时上报给认证中心 → 认证中心存进 sys_permission(type=menu) 供授权界面展示（L1）→ 登录后按授权结果下发本应用菜单集合 → 前端 <SidebarMenu> 渲染（L2）。
关键：认证中心是「存 + 授权」，不是「定义」。所以「应用没有菜单」对它毫无影响——不上报就不出现，等有了菜单再加一个 yml。
✅ 良哥已拍板：放应用侧（2026-09-10）。连带确定的几件事：
① 管理界面不做「建菜单」功能，只做「谁可见」的授权配置（§8 的两张界面）。
② 菜单变更不需要动认证中心——加菜单 = 改应用自己的 yml + 应用发版，中心零改动。
③ 因此菜单上报必须是「全量覆盖」语义——中心以应用最后一次上报为准，才能识别出「已删除的菜单」并标记失效。
④ 也意味着中心不校验菜单路径是否有效（那是应用的事），中心只存元数据 + 授权关系。
应用侧（定义+上报） 认证中心（存储+授权） 应用侧（消费）
menu-registry.yml ──启动上报──▶ sys_permission(type=menu) ──下发──▶ GET /auth/permissions

五、统一菜单元数据模型
把 cosmic 的 MENU_REGISTRY 补全成通用模型（它缺分组、排序、隐藏、外链这几项）：
# <app>/src/main/resources/menu-registry.yml —— 应用自己的菜单树
menus:
 - key: dashboard
 title: 看板
 icon: DataAnalysis
 path: /dashboard
 order: 10
 - key: resource # 分组节点（对应 el-sub-menu）
 title: 资源管理
 icon: Cpu
 order: 20
 children:
 - { key: hosts, title: 主机管理, icon: Monitor, path: /hosts, order: 21 }
 - { key: services, title: 服务管理, icon: Connection, path: /services, order: 22 }
 - { key: credentials, title: 凭据管理, icon: Key, path: /credentials, order: 23 }
 - key: admin
 title: 系统工具
 icon: Tools
 order: 90
 min-role: admin # 角色下限（沿用 cosmic 语义）
 children:
 - { key: users, title: 用户管理, icon: User, path: /users, order: 91 }
 - key: docs
 title: 使用文档
 icon: Document
 path: https://docs.marschat.online
 external: true # 外链菜单
 order: 99
 - key: project-detail
 title: 项目详情
 path: /projects/:id
 visible: false # 隐藏菜单：有路由但不上侧边栏
字段 | 说明 | 对应表字段 | 
key | 稳定标识，权限点用它：<client>:menu:<key> | sys_permission.code | 
title / icon | 展示名与图标名 | name / meta.icon | 
path | 路由路径或外链地址 | meta.path | 
children | 分组或子菜单 | parent_id 自关联 | 
order | 同级排序 | sort | 
min-role | 角色下限，低于此角色不可见（只能做减法） | meta.min_role | 
visible | 是否上侧边栏（详情页等设 false） | meta.visible | 
external | 是否外链 | meta.external | 
跨语言对齐：cosmic 是 Python 后端，也用同一套 yml 格式。它的 MENU_REGISTRY（现在写死在 studio.py）平移到 menu-registry.yml 即可，未来若加 Python 版上报客户端，格式一致、不用二次翻译。
六、菜单权限的双重模型
cosmic 现在这套「角色下限先卡 + 用户白名单做减法」是正确且实用的，建议直接作为平台标准：
层 | 数据 | 谁配 | 作用 | 
角色级 | sys_role_permission | 管理员在「角色管理」配 | 定义某角色默认能看到哪些菜单（上限） | 
用户级 | sys_user_menu_override（即 cosmic 的 menu_perms） | 管理员在「用户管理」配 | 在角色上限内进一步做减法（收窄），永不越权 | 
未配置 | NULL / 无记录 | — | 跟随角色默认 | 
为什么是「只能做减法」：cosmic 的注释写得很清楚——「菜单权限只能做减法、不能越权」。这保证了不管用户级怎么配，都不可能超出角色给出的范围，避免「用户级配置变成提权后门」。
这条规则对用户管理界面的意义是：勾选树应该只显示该角色已授权的菜单，而不是全量菜单。否则管理员会误以为勾了就能给。
未配置时的默认策略
A. 默认全部可见
宽松。问题：新加的菜单对所有角色自动可见，敏感菜单容易漏配而暴露。
B. 默认全部不可见
严格。问题：角色没配好时所有人菜单全空，误以为系统坏了。
C. 默认跟随角色默认 推荐 = cosmic 现状
用户级未配置 → 用角色级结果；角色级也未配置 → 用 min-role 兜底。逐层回退，不会出现「全空」也不会「全开」。
七、三层同源（菜单 / 路由 / 接口）
必须堵的洞：菜单藏了，但用户直接敲 URL 仍能进页面；前端拦住了，但接口仍可被直接调用。
「菜单权限」如果只挡菜单，等于没挡——这是典型的安全假象。
层 | 手段 | 依据 | 
菜单 | <SidebarMenu> 只渲染有权限的项 | 权限集合里的 menu:* | 
路由 | 守卫校验 meta.requiredPermissions，不在集合内跳 403 | 同一份权限集合 | 
接口 | 后端 @RequirePermission("<client>:api:<key>") | token 里的 permissions | 
顺带修掉 cosmic 守卫的一个脆弱点
cosmic 现在按菜单集合做 URL 拦截，但写了两段很长的注释解释一个坑：
// 权限守卫二次执行：直输 URL 整页刷新时 watch 跑在 menus 加载前（空数组不拦），
// 路由此后不再变化，守卫会永久失效——菜单加载完在这里补判一次
根因是「先挂载路由、后异步拉菜单」这个顺序——守卫在权限还没到手时就跑过了，只能靠事后补判兜底。补判能work，但这是治标，而且注释里已经出现「首屏直链漏页签」「未授权页签要一并清掉」等连带问题（都是同一个根因的衍生）。
公共组件里的正确做法：bootstrapMarschatApp() 在挂载路由之前先拉权限，拉不到就阻塞导航（不进入应用页面）。这样守卫天然只需执行一次，不需要「二次补判」，那些衍生问题也一并消失。
顺带统一 403 语义：无权限跳统一 403 页，而不是各应用自己 replace 到第一个菜单。

九、新应用接入菜单的三步
1
写 menu-registry.yml 可选，没有菜单就跳过
把菜单树声明出来（§5 的格式）。这是把「模板标签」变成「数据」的那一步，也是唯一需要手动做的工作。
2
启动时自动上报 零代码
auth-core 的 MenuRegistryReporter 读该文件，启动时调 PUT /admin/clients/{clientId}/menus。应用侧只写一行配置开关（见《配置化接入方案》§7 的 menu-report）。
3
前端换成公共组件渲染
删掉 MainLayout.vue 里的硬编码 el-menu-item，换成 <SidebarMenu :menus="menus">，menus 来自 useMenus()（自动拉 GET /auth/permissions 并按权限过滤）。
接入成本对照
场景 | 要做的事 | 工作量 | 
新应用，有菜单 | 写 yml（1 个文件）+ 前端换组件 | ~半天 | 
新应用，无菜单 | 什么都不用做 | 0 | 
等以后有菜单了 | 加一个 yml 文件，不改认证中心、不改公共组件 | ~1 小时 | 
这正好回答了你担心的「很多应用没菜单」：菜单上报是可选的。没菜单的应用照常接入 SSO 和权限体系（只是没有可分配的菜单项）；将来有了菜单，加一个 yml 就行，认证中心和公共组件都不用动。菜单的有无，对平台零影响。
十、存量改造与边界情况
10.1 存量应用改造（4 个硬编码菜单的应用）
应用 | 改造内容 | 性质 | 
kb-ops-web | 从 MainLayout.vue 提取 4 组 25 项 → menu-registry.yml（已有 el-sub-menu 分组，正好映射 children） | 纯机械提取 | 
infra-monitor-web | 提取 ~11 项 | 纯机械提取 | 
kb-web | 提取 ~50 项（最大） | 量大但同性质 | 
myfrp | 提取 4 项；v-if="role === 'ADMIN'" 改为 min-role: admin | 顺带把硬编码角色判断规范化 | 
改造是「提取」而非「重写」：模板里已有的 title／icon／path／分组顺序，逐条抄进 yml 即可，无需重新设计菜单结构。而且可以先不动前端——第一版只上报菜单给认证中心，让权限界面有数据可配，前端渲染改造放到后面单独做。这样风险可以切开。
10.2 几个必须想清楚的边界
情况 | 处理 | 
菜单有但页面没发版（先配权限后有页面） | 以应用上报为准——应用没发版就不会上报新菜单，权限界面也就看不到。天然避免 404。 | 
应用下线/改名 | 菜单随上报消失。需要处理「孤儿权限」——建议上报接口做全量覆盖（不存在的 key 标记失效），而不是增量追加。 | 
隐藏菜单（详情页、编辑页） | visible: false —— 有路由、可直链、但不上侧边栏，且仍需在权限集合内（否则直链能进）。 | 
外链菜单 | external: true，不过路由守卫，但仍可授权控制可见性。 | 
菜单项改名 | key 是稳定标识、title 只影响展示。改名不动 key，权限配置不会失效。 | 
跨应用菜单（一个菜单跳另一个系统） | 本质是外链，走 external；平台级导航（portal 系统卡片）另归 apps-registry.yml 管。 |

⚠️ 唯一还需要注意的代价
放应用侧之后，中心的菜单列表是「应用报上来的」，不是「中心自己知道的」。所以会出现两个特性，属于该方案的固有属性而非缺陷：
① 新菜单在应用发版前不会出现在授权界面——因为还没上报，配不了。这恰恰是好事：避免了「菜单配了但页面还没有」的 404。
② 应用停用或未启动时，其菜单仍保留在中心（最后一次上报的结果）。如果想看到「实时存活」状态，需要靠 sys_app_client.last_sync_at 来体现——上报时间过久即视为可疑。这一点已在 §5 的 sys_app_client 表设计中预留。
