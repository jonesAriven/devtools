关键缺口
Token 里的角色是标量——JWT 只带 role: admin|user，没有应用级权限、没有菜单权限。这就是「无法回答谁有哪些系统权限」的根源。
realm 概念建了但空转——user.realm_id 字段和注释「同 realm 内应用可 SSO，跨 realm 隔离」都在，但线上全部值是 kb，多账号池能力没启用。
没有 RBAC 表——不存在 sys_role / sys_permission / sys_user_role / sys_role_permission 任何一张。
email 无唯一约束——user 表只有 uk_username 和 idx_phone，email 既无索引也无唯一性。账号关联、找回密码全都建立在不牢靠的基础上。
OIDC 客户端缺两个——已注册 7 个（portal / inframon / kbops / tokenhub / kbweb / activecode / memory），cosmic-studio 和 frp-manager 未注册。
cosmic 重复造轮子——它自己实现了 MENU_REGISTRY（8 个菜单带 min_role 下限）+ 用户级 menu_perms JSON 白名单（角色做减法），逻辑是对的，但只在 cosmic 内部生效，其他应用享受不到。
portal 的 JIT 关联键不牢——按 username 关联而非 IdP 的 sub，用户改名或邮箱变更就断链。
用户管理不达标——listForAdmin 全量返回无分页、无关键字搜索、增删改零审计日志、无事务、禁用用户不踢下线（JWT 仍有效）。
一句话总结现状：用户要在 5 个地方各建一次账号，权限散落在各应用内部，没有任何一处能回答「张三在哪些系统有什么权限」。而且 auth-center 被 12 个应用直接依赖，是全局枢纽，任何改造必须向后兼容。
二、设计原则
1. 一处管人
身份只有一个真源。其他应用要么完全弃用本地账号表，要么只保留一份由 SSO 驱动的映射，绝不各自维护密码。
2. 一人一号、多身份
把 email / phone / 微信从 user 表里拆出来成身份表。唯一约束天然成立，天然支持一个用户绑多个邮箱。
3. 授权三层分离
平台角色（跨应用）／应用角色（每应用）／权限点（菜单与接口）分开，各管各的语义，不混成一个 role 字段。
4. 应用自注册权限
菜单树是应用自己的资产，由应用上报给认证中心统一存储与下发。不在认证中心硬编码各应用的菜单。
5. 向后兼容优先——auth-center 是 12 个应用的枢纽，所有改动以「新增字段、新增接口」为主，不改老契约。6. 收敛优于并存，但每步可独立发布——不追求一次大爆炸，每个阶段都能单独上线、单独回滚。
三、目标架构
3.1 身份层
核心动作：把 user 表里的 email / phone / wechat_openid 三列拆成独立的身份表。这是业界处理「账号关联」的标准做法，比「给 email 加个唯一索引」根本得多。
表 | 职责 | 关键字段 | 
user | 人 | id, username, nickname, avatar, status, realm_id, deleted | 
user_identity | 身份绑定 | id, user_id, provider(email|phone|wechat|github), identifier, verified, is_primaryUNIQUE(provider, identifier) | 
user_credential | 凭证 | user_id, type(password|totp), secret(BCrypt), updated_at | 
为什么值得拆：① UNIQUE(provider, identifier) 让邮箱唯一性成为数据库层面的事实，不再靠应用层查重；② 一个用户可绑多个邮箱、多个社交账号，「账号关联」就是插一行记录；③ 换邮箱不动 user 主键；④ 邮箱验证码登录、社交登录、手机登录共用同一套表，不用再加列。
3.2 授权层：三层 RBAC
采用 Keycloak 的 Realm Role / Client Role 模型——这是目前多应用 SSO 场景下的业界标准，能同时满足你说的两个诉求（「每个用户有哪些系统的权限」+「对应系统的菜单权限」）。
层 | 名称 | 作用域 | 示例 | 回答的问题 | 
L1 | 平台角色 realm_role | 跨应用全局 | superadmin / admin / user | 能不能进用户管理、是不是超级管理员 | 
L2 | 应用角色 client_role | 单个 OIDC client | cosmic-studio:admin、marschat-kbweb:editor | 在某个系统里是什么身份 | 
L3 | 权限点 permission | 单个 client 的资源 | cosmic-studio:menu:vocab、marschat-kbweb:api:doc:delete | 具体能看哪个菜单、调哪个接口 | 
支撑表结构：
表 | 说明 | 
sys_role | id, scope(platform|client), client_id, code, name, description —— L1 与 L2 共存一表，用 scope 区分 | 
sys_permission | id, client_id, type(menu|api|action), code, name, parent_id, sort —— 菜单树靠 parent_id 自关联 | 
sys_role_permission | role_id, permission_id —— 角色拥有哪些权限点 | 
sys_user_role | user_id, role_id, client_id, granted_by, granted_at —— 谁在什么系统里是什么角色，带授权人和时间（审计需要） | 
sys_role_composite | parent_role_id, child_role_id —— 角色继承，比如「应用管理员」自动含「编辑者」 | 
sys_app_client | client_id, name, status, menu_registry_json, last_sync_at —— 应用注册表，含它上报的菜单树 | 
3.3 菜单权限的工作流
注册
应用上报自己的菜单树
应用发布时调 PUT /admin/clients/{client_id}/menus 上报菜单数组。cosmic 现有的 MENU_REGISTRY 可以直接复用，改成上报接口即可。
存储
认证中心汇总成统一权限树
落进 sys_permission（type=menu）。用户管理界面据此渲染成「系统 × 菜单」的勾选树。
授权
在用户管理界面勾选定权限
勾选写入 sys_user_role / sys_role_permission。这就是你要的「每个用户有哪些系统的权限」页面。
下发
登录后前端拉取本应用权限集合
GET /auth/permissions?client=<id> → 路由守卫拦截 + 菜单按集合渲染。后端用 @PreAuthorize 校验权限点。
3.4 Token 契约（新增字段，老客户端可忽略）
{
 "sub": "1", // 稳定主键，所有映射只用它
 "uid": "1",
 "username": "admin",
 "realm": "kb",
 "role": "superadmin", // 平台角色，原有字段升级
 "permissions": ["cosmic-studio:menu:vocab", "..."], // 本 client 权限点（新增）
 "resource_access": { // Keycloak 式应用角色（新增）
 "marschat-kbweb": { "roles": ["editor"] }
 }
}

四、五个关键决策（含选项对比）
决策 1 · 账号池收敛策略
A. 全量收敛 — 所有应用废弃本地账号表
最彻底，但 cosmic 的业务表有外键指向 users.id，一次性迁移风险高。
B. 保留本地表靠 JIT 同步 portal 现状
改造量最小，但密码仍是两套，权限仍然分散，问题没根治。
C. 混合收敛 推荐
纯 SSO 应用直接废弃本地表；有业务外键的应用先 JIT + 映射表过渡，再逐步把外键迁到 SSO 的 uid。风险可控且能真正收敛。
决策 2 · 身份信息存列还是存表
A. 给 user.email 加唯一索引
改动最小，但一个用户只能有一个邮箱，多身份绑定和账号关联都做不了。
B. 拆 user_identity 表 推荐
既然要重构授权，一次到位。唯一性由数据库保证，账号关联变成插一行，后续加社交登录零成本。
决策 3 · 角色模型
A. 保持标量 role，各应用自管
现状。回答不了「谁有哪些系统的权限」。
B. 扁平 user_role 关联表
能多角色，但没有客户端维度，权限点无处安放。
C. Keycloak 三层模型 推荐
业界标准，天然支持跨应用角色 + 每应用细粒度 + 角色组合继承。cosmic 的私有模型可直接映射进来。
决策 4 · 库名 kb_auth
A. 不改
省事，但一个平台级公共组件顶着 kb_ 前缀，名不副实，后续接入非 kb 体系应用会更别扭。
B. 改 marschat_auth 推荐
与 marschat-components / auth-center 命名对齐。application-prod.yml 里库名走 ${MYSQL_DATABASE:kb_auth} 环境变量，改库名零代码改动，只需 dump/restore + 改 compose env，回滚就是改回 env。
决策 5 · 菜单权限的实现方
A. 各应用自管
cosmic 现状。每个应用各写一份菜单注册表 + 权限过滤逻辑，重复劳动且标准不一。
B. 应用上报 → 认证中心统一存储下发 推荐
把 cosmic 的 MENU_REGISTRY 抽象成通用上报接口，一次实现全部应用受益，用户管理界面也能统一展示。
五、SSO 用户与独立用户的映射
这是你特别问到的一点。业界主流有三条路，结论是前两条组合使用，第三条不采用。
方案 | 原理 | 适用场景 | 取舍 | 
JIT Provisioning首次登录自动建号 | 
用户第一次 SSO 登录时，按 IdP 的 sub 自动在本地建一条镜像记录 | 
新应用快速接入 | 
推荐 portal 已在用，改关联键为 sub 即可 | 
Account Linking按已验证邮箱关联 | 
本地已存在同邮箱账号时，自动或手动把两者关联起来 | 
存量账号迁移期 | 
推荐 迁移期一次性使用，之后不再需要 | 
SCIM 2.0集中目录同步 | 
认证中心作为目录服务，向各应用推送增删改 | 
企业级多租户 | 
不采用 个人级基础设施用不上，维护成本过高 | 
推荐组合：① 统一关联键为 SSO 的 sub（不可变、永不变），本地业务表存 subject 而不是 username；② 迁移期用 已验证邮箱自动关联一次，把存量本地账号挂到对应的 SSO uid 上；③ 关联完成后，本地账号表逐步降级为「只读映射」直到下线。
顺带修掉一个隐患：portal 现在按 username 做 JIT 关联。用户改名会让映射断裂，进而可能建出重复账号。改成 sub 后这类问题不会再发生。

七、影响面与风险
枢纽影响面（必须尊重）
auth-center12 个应用直接依赖 / 12 个传递影响 —— 全局最大枢纽

风险与缓解
风险 | 缓解措施 | 
改 auth-center 波及 12 个应用 | 只做增量（新增字段/接口），不改老契约；token 新字段老客户端可忽略 | 
库改名导致应用连不上 | 走 env 变量，改名前后各做一次 dump；异常时改回 env 立即回滚 |
